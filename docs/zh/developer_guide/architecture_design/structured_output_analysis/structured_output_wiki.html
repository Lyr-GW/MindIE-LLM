2NPU 上纯 torch op 实现 bitmask→logits
python# structured_output_bitmask.py:46-65
def apply_token_bitmask_inplace_npu(logits, bitmask, vocab_size):
    mask_expanded = torch.repeat_interleave(bitmask, 32, dim=-1)
    bit_indices = torch.arange(32, device=logits.device, dtype=torch.int32).repeat(bitmask.shape[-1])
    bit_masks = (mask_expanded >> bit_indices) & 1
    mask_coverage_len = bit_masks.shape[-1]
    effective_len = min(vocab_size, mask_coverage_len)
    logits[..., :effective_len] = logits[..., :effective_len].masked_fill_(bit_masks == 0, float("-inf"))
    if vocab_size > effective_len:
        logits[..., effective_len:vocab_size] = float("-inf")

对照 vLLM：vLLM 用 xgrammar 提供的 CUDA kernel 直接完成。NPU 平台无现成 kernel，避免上 CANN 算子开发，用通用 op 组合达成"够用"。位运算正确性证明见第 6 章。

3双计数器 num_processed_tokens / num_tried_tokens — 真实踩坑 DEEP BUG
⚠️ 强烈推荐写进简历的深度 bug

xgrammar C++ 内部 replay buffer 对 reject 的 token 无条件入队（用于状态机回溯）。如果只用 num_processed_tokens 作切片下标：

  1. 出现 reject → buffer 实际位置已前进，下次切片错位
  2. 后续合法 token 被误丢
  3. FSM 永远无法接受新 token → 序列空转
python# structured_output_grammar.py:148-181

4编译缓存：短 key + FIFO + 抗碰撞
python# structured_output_manager.py:1057-1080
def _compile_grammar(self, output_type, grammar_spec):
    cache_key = StructuredOutputManager._get_cache_key(output_type, grammar_spec)
    if cache_key in self._grammar_cache:
        stored_spec, compiled = self._grammar_cache[cache_key]
        if stored_spec == grammar_spec:        # 抗哈希碰撞
            return compiled
    backend = self._ensure_backend()
    compiled = backend.compile_grammar(output_type, grammar_spec)
    if len(self._grammar_cache) >= self.config.grammar_cache_size:
        first_key = next(iter(self._grammar_cache))   # FIFO
        del self._grammar_cache[first_key]
    self._grammar_cache[cache_key] = (grammar_spec, compiled)
    return compiled

@staticmethod
def _get_cache_key(output_type, grammar_spec):
    h = hashlib.sha256(grammar_spec.encode()).hexdigest()
    return f"{output_type.value}:{h}"
  • SHA-256 短 key：避免 100 KB schema 当 dict key 导致 hash 慢
  • value 存原 spec：抗 sha256 碰撞
  • FIFO 而非 LRU：评估生产 distinct schema < 50，FIFO 实现 O(1)：next(iter(d)) 拿最旧键

6. 专题 B：NPU bitmask 位运算正确性证明 #

6.1 输入约定

📖 xgrammar 约定

token id t 是否允许 = (bitmask[batch_idx, t // 32] >> (t % 32)) & 1

即 bit 顺序 = LSB 先：第 0 个 bit 表示 token id c*32 + 0，……第 31 个 bit 表示 c*32 + 31。

6.2 实现回顾

pythonmask_expanded = torch.repeat_interleave(bitmask, 32, dim=-1)
bit_indices = torch.arange(32).repeat(W)
bit_masks = (mask_expanded >> bit_indices) & 1
logits[..., :L].masked_fill_(bit_masks[..., :L] == 0, -inf)

6.3 元素索引证明

Step 1：mask_expanded 的索引映射

torch.repeat_interleave(bitmask, 32, dim=-1) 的语义：

  • 输入 bitmask[b, c]（c 为列下标）
  • 输出 mask_expanded[b, j]，对应 bitmask[b, j // 32]

因此：mask_expanded[b, j] = bitmask[b, j // 32]

Step 2：bit_indices 的索引映射

torch.arange(32).repeat(W) 生成 [0, 1, ..., 31, 0, 1, ..., 31, ...]，长度 W*32。

因此：bit_indices[j] = j % 32

Step 3：合成

bit_masks[b, j] = (mask_expanded[b, j] >> bit_indices[j]) & 1
                = (bitmask[b, j // 32] >> (j % 32)) & 1

由于 j = t（输出位置即 token id）：

bit_masks[b, t] = (bitmask[b, t // 32] >> (t % 32)) & 1
✅ 与 xgrammar 约定完全一致

6.4 边界条件分析

边界 1：vocab_size 不是 32 的倍数

设 V = 32*W - r，其中 0 ≤ r < 32。则 mask_expanded 长度为 W*32 = V + r，比 logits 多 r 个位置。

pythoneffective_len = min(vocab_size, mask_coverage_len)  # = V
logits[..., :effective_len].masked_fill_(bit_masks[..., :effective_len] == 0, -inf)

仅取前 V 列，多余 r 个位置不参与 mask。✅ 正确。

边界 2：vocab_size > mask_coverage_len

理论上不会触发；但若调用方传错，代码兜底将尾部置 -inf，等价于"尾部全部禁止"。✅ 安全。

边界 3：xgrammar 中的"全允许"（-1 = 0xFFFFFFFF）

-1 的 32 位二进制全 1，所有 bit 均为 1，移位 + & 后所有 token 都通过。✅ 一致。

边界 4：负数右移的语义陷阱

⚠️ 严格证明

设 x 为任意 int32，第 k 位（0 ≤ k < 32）的值为 b_k。证明 (x >> k) & 1 = b_k，无论 >> 是算术还是逻辑右移。

  • 逻辑右移：x >> k 高位补 0，低位丢弃 → 结果第 0 位 = 原第 k 位 = b_k
  • 算术右移：x >> k 高位填符号位 b_31，低位丢弃 → 结果第 0 位 = 原第 k 位 = b_k

两种右移仅影响高位，最低位都等于原第 k 位。& 1 仅取最低位，故二者等价。∎

10. 可外推的工程经验 #

  1. 抽象层"先准备好，但不过度实现" — GrammarBackend 抽象成 enum + 单类 if 分发，足以应付当下，又留有口子。比起一上来就实现 4 个后端的"完美设计"，这种渐进式更现实。
  2. 缓存的 key 设计要同时考虑 hash 性能 + 抗碰撞 — 大对象做 key 时一定要短 key + 原对象比对的双重保护。
  3. 对依赖库的"内部约定"要做防御 — 双计数器是因为 xgrammar 的 replay buffer 行为不在公开 API 文档里。任何依赖第三方 C++ 库内部状态的代码，都应该写一层"约定即代码"的封装。
  4. 执行顺序差异要靠注释 + 单测固化 — prefill / decode 的顺序差异肉眼几乎不可见，必须用单测把"反例"固化下来。
  5. 平台差异不一定要靠定制算子解决 — 当通用 op 组合"够用"时（亚 ms 级），优先选可移植性。CANN 算子开发周期长、维护成本高，要算 ROI。
  6. fail-fast vs rollback — 看场景。GPU + 小 batch + 在线推理偏 rollback；NPU + 大 batch + 吞吐导向偏 fail-fast。

12.3 grammar_bitmask 批量填充

python# structured_output_manager.py:382-422
def grammar_bitmask(self, cache_ids, apply_bitmask_flags=None):
    if cache_ids is None or len(cache_ids) == 0:
        return None

    has_any_grammar = any(state_key in self._request_grammars for state_key in cache_ids)
    if not has_any_grammar:
        return None                                  # 提前返回，避免无谓的 fill

    batch_size = len(cache_ids)
    if batch_size > self._bitmask_buffer.shape[0]:   # 整批扩容（不是 per-call）
        self._bitmask_buffer = np.zeros((batch_size, self._bitmask_width), dtype=np.int32)

    bitmask = self._bitmask_buffer[:batch_size]
    bitmask.fill(self._full_mask)                    # 全 -1：默认全允许

    for idx, state_key in enumerate(cache_ids):
        if apply_bitmask_flags is not None and not apply_bitmask_flags[idx]:
            continue
        grammar = self._request_grammars.get(state_key)
        if grammar is None or grammar.is_terminated():
            continue                                  # 已终止：保持 -1
        try:
            grammar.fill_bitmask(bitmask, idx)        # xgrammar 写入第 idx 行
        except Exception as e:
            logger.warning(f"Failed to fill bitmask for state_key {state_key}: {e}")
            # 失败不阻塞整批

    return bitmask.copy()                            # 出口拷贝
3 个防御点
  1. has_any_grammar 提前剪枝：避免空批次的无谓 fill
  2. try/except per-序列：单个失败不影响其他序列
  3. bitmask.copy()：buffer 是共享缓冲，必须拷贝出去

        if grammar is None or grammar.is_terminated():
            continue                                # 无 grammar 或已终止：保持 True
        try:
            if i < len(flattened_token_ids):
                token = int(flattened_token_ids[i])
                is_accepted = self._accept_tokens_on_grammar(
                    normalized_state_key, grammar, [token])
                is_accepted_array[i] = is_accepted
        except Exception as e:
            logger.warning(...)
            is_accepted_array[i] = False            # 异常视为拒绝（保守）
    return is_accepted_array

14. Suffix Search 兜底算法剖析 #

14.1 算法目标

当 replay_tokens 整体喂给 grammar 时起始位置即被 reject，意味着前缀很可能包含了不属于结构化输出部分的内容（如 prompt template、<|assistant|> 等 special token）。

14.2 算法实现

python# structured_output_manager.py:957-970
search_start = max(1, len(replay_tokens) - 512)
for start_idx in range(search_start, len(replay_tokens)):
    self.clear_requests([state_key])
    if not self._init_grammar_from_response_format(state_key, response_format):
        return 0
    suffix_tokens = replay_tokens[start_idx:]
    if self.accept_tokens(state_key, suffix_tokens):
        logger.debug(...)
        return len(suffix_tokens)
return 0

14.3 复杂度分析

设 N = len(replay_tokens)。

  • 搜索起点：max(1, N-512)，意味着只在最后 512 个 token 中找起点
  • 迭代次数：最多 min(N, 512) 次
  • 每次迭代：清空 grammar + 重建 + accept 一段后缀
    • 清空：O(1)
    • 重建：O(1)（grammar 已缓存，只是 create_grammar 创建新 matcher）
    • accept 一段后缀：O(suffix_len)
  • 总复杂度：最坏 O(512²) ≈ 262144 个 token accept 操作

14.4 为什么是 512？

  • 大多数结构化输出场景中，JSON 输出长度 < 512 token（典型 200-300）
  • 把搜索窗口限制在 512 防止退化为 O(N²)
  • 若 JSON 真超过 512，suffix search 仍可能找不到可重放后缀；此时 grammar 退回初始态，由 D 节点重新生成

14.5 算法正确性

📐 关键观察

若 accept(replay_tokens) 失败但 accept(replay_tokens[k:]) 成功，意味着：

  • replay_tokens[:k] 不属于 schema 描述的字符串
  • replay_tokens[k:] 是从 schema 起始符开始的合法序列

当前算法选最小的合法 k（最先成功的 start_idx），即"尽量保留更多的回放历史"。

14.6 改进方向

  1. 二分搜索：若 grammar 接受 [k:] 单调（接受 k → 接受 k+1），可二分；但实际不一定单调（k 不同对应不同的起始 FSM 状态）。
  2. 基于 token 内容的剪枝：先扫描找 { token 出现的位置，仅在这些位置尝试。需引入 tokenizer 反查。
  3. 离线索引：把 schema 的"合法起始 token 集合"预计算，跳过明显不可能的 start_idx。

17. 面试 30 题答题库 #

设计层（10 题）

Q1：为什么不直接用 vLLM 已有的实现？
MindIE 是面向昇腾 NPU 的独立推理引擎，与 vLLM 完全不同的运行时（PTA、CANN、ATB），无法直接复用。但参考了 vLLM 的设计思路（xgrammar 后端选型、bitmask 形状）。
Q2：为什么选 xgrammar 而不是 outlines / llguidance？
(1) xgrammar 性能领先（论文实测 100x+ vs outlines）；(2) C++ 实现，与 NPU pipeline 集成阻力小；(3) vLLM v1 默认后端，社区证明可靠。outlines 用 numba JIT，对 NPU 不友好。
Q3：为什么用 sha256 而不是 md5？
sha256 避免哈希碰撞攻击。性能上 sha256 在现代 CPU 上有 SHA-NI 指令加速，与 md5 差距 < 2x。短 key 长度差异（64 vs 32 字符）不重要。
Q4：为什么是 FIFO 而不是 LRU？
(1) Python dict 自然保序，FIFO 实现 O(1) 复杂度；(2) 评估生产环境 distinct schema 数量 < 50，cache 容量 100 永不驱逐；(3) LRU 需额外维护双向链表或 OrderedDict.move_to_end，增加每次访问开销。
Q5：为什么 fail-fast 而不是 rollback？
(1) NPU pipeline 重排成本高；(2) reject 在实际生产中极少发生（< 0.1%），不值得为这个 case 设计 rollback 路径；(3) fail-fast 让客户端可观察（end_reason=7），便于上层决定 retry。
Q6：为什么把 bitmask 放在 SamplingMetadata 而不是 InputMetadata？
bitmask 是 sampler 用的，与采样链路（LogitsHandler）紧耦合；放 SamplingMetadata 让 sampler.split / sampler.merge 时可以一起切分，避免下标错位。
Q7：response_format 字符串为什么要在 DictContext 持久化？
Decode 阶段不重新发送 batch_response_format（节省 IPC 带宽），按 cache_id 反查；与 stop_strings、stop_token_ids 一致的设计模式。
Q8：grammar_init 的 state_key 为什么用 cache_id 而不是 sequence_id？
(1) cache_id 是 batch_context 的内部 handle，与 sequence_id 1:1 但语义更内聚；(2) fork_context 时子序列分配新 cache_id；(3) 减少跨模块依赖。
Q9：为什么 prefill 后要重新算 bitmask？
process_batch_for_generation 第一次只是 init grammar 到初始态；如果存在 PD 分离的 predicted_token_ids，必须 replay 完后再算 bitmask，否则用的是初始态的约束（等价于"重发了第一个 token"）。
Q10：你在哪一步引入了双计数器？是先有 bug 还是先有设计？
是 bug 驱动的。最初只有 num_processed_tokens，在 PD 分离场景压测中发现某些请求 grammar 状态卡死。dump xgrammar replay buffer 后发现 reject token 占位但 num_processed_tokens 不增，导致下次切片错位。修复后引入第二个计数器并加单测。

实现层（10 题）

Q11：apply_token_bitmask_inplace_npu 的 5 步算法，能用更少的 op 实现吗？
理论可以用 torch.bitwise_and(bitmask.unsqueeze(-1), 1 << torch.arange(32))，再 reshape 后展平。本质 op 数差不多，可读性稍差。或者用 unfold，但 NPU 上未必有原生支持。
Q12：为什么 bit_indices 每次都重新 alloc？
实现疏忽，这是个明确的优化点。可以缓存为 module 级常量（按 device、dtype、W 三维 key cache）。预估省 ~10% 延迟。
Q13：bitmask.copy() 不能省掉吗？
不能。_bitmask_buffer 是共享缓冲，下次调用会覆盖。如果不 copy，sampler 真正读取时可能拿到别的 batch 的数据（异步路径下尤其危险）。
Q14：grammar 编译失败时为什么不抛异常向上传？
(1) 单个请求失败不应拖垮整批；(2) 上层 _init_grammar_from_response_format 返回 False 后，process_batch_for_generation 跳过该序列，bitmask 行保持 -1（不施加约束），相当于自动降级为非约束模式。
Q15：为什么 _resolve_replay_tokens 优先选 predicted_token_ids？
predicted_token_ids 来自 P 节点，是"权威"输出；sampling_metadata.output_token_ids 是 D 节点本地视角，可能不完整（首次 decode 时为空）。优先权威源避免状态歧义。
Q16：suffix search 的 512 这个魔法数怎么定的？
经验值，覆盖 95% JSON 输出长度。需要可配置但当前未暴露。
Q17：_accept_tokens_on_grammar 的额外日志会有性能影响吗？
所有日志都是 logger.debug，生产环境 logger 级别 INFO 时不会执行字符串格式化。但 parse_bitmask_allowed_tokens 在日志路径外也调用，这是个潜在优化点。
Q18：fork_context 时复制 response_format，但当前互斥了 best_of>1，是不是死代码？
是预留代码，为将来解禁互斥准备。代码本身无副作用且开销 O(1)，保留更安全。
Q19：clear_finished_requests 的时机？
在 BatchContext.clear_context_by_handles（line 624-626）调用，时机是序列被 OutputFilter 标记结束 → cache 清理 → grammar 一并释放。释放后 _request_grammars 不再持有 matcher，xgrammar C++ 资源自动回收。
Q20：异步路径下 update_states_after_sampling 的执行点？
在 forward_loop 内 sample 之后立即执行（plugin_manager.py:751），通过 sampling_output.is_structured_accepted 字段把结果带到 postprocess。同步路径在 postprocess 内执行。两条路径都会经过 compute_structured_output_accepted。

(1) 单元测试：构造已知 bitmask（如只允许 token 0、5、31），调用 apply 后断言 logits[0,5,31] 不变、其他为 -inf；(2) 端到端测试：跑真实 schema，检查输出能 json.loads。

当前主要靠 debug 日志，没有 metrics。未来应加：grammar 编译耗时直方图、cache 命中率、reject 率、bitmask apply 延迟。

系统层（5 题）

Q26：为什么不在 C++ 直接做 bitmask 应用？
(1) sampler 在 Python 层，logits 已经在 Python torch.Tensor；(2) 跨 Python/C++ 调用 logits tensor 涉及 GIL 与 device 同步；(3) Python 实现易于迭代和调试。
Q27：如果 vocab 突然变大（如 200K → 500K），bitmask 内存会爆吗？
500K vocab → 单序列 62 KB，批 256 → 15 MB。仍可接受。问题更在 fill_bitmask 的 xgrammar 内部成本（取决于 schema 复杂度）。
Q28：多 GPU/NPU 部署时，每个 rank 都会编译 grammar 吗？
是。每个 rank 有独立的 StructuredOutputManager 实例和 cache。可以优化为编译产物广播（但 xgrammar CompiledGrammar 是 C++ 对象，不易序列化）。当前不是瓶颈（cache hit 后免费）。
Q29：tokenizer 不一致的多模型部署怎么办？
当前 StructuredOutputManager 持有单一 tokenizer，多模型部署需要每模型独立 manager。未来可以扩展为 tokenizer_id → manager 字典。
Q30：xgrammar 升级会兼容吗？
通过 _get_xgrammar_module() 懒加载，导入失败降级；版本号在初始化时记录但未做版本兼容判断。建议加版本号检查，xgrammar 0.1.x → 0.2.x 有 API 变更。

19. JSON Schema → FSM 编译图解 # v3 新增

19.1 xgrammar 编译过程概述

xgrammar 的核心机制：把 JSON Schema 编译为下推自动机（PDA, Pushdown Automaton），并预计算每个状态可接受的 token bitmask（cache 起来）。

19.2 简单 Schema 的编译产物

以 schema {"type":"object","properties":{"name":{"type":"string"}},"required":["name"]} 为例。

stateDiagram-v2 [*] --> S0: 初始 S0 --> S1: '{' S1 --> S2: '"' S2 --> S3: 'n' S3 --> S4: 'a' S4 --> S5: 'm' S5 --> S6: 'e' S6 --> S7: '"' S7 --> S8: ':' S8 --> S9: '"' S9 --> S9: 任意字符串字符 S9 --> S10: '"' S10 --> S11: '}' S11 --> [*]: 终止 note right of S0 允许 whitespace (any_whitespace=True) end note note right of S9 进入字符串值状态 end note
⚙️ 实际复杂度

真实 PDA 远比上图复杂：

  • JSON 字符串中允许 escape sequence（\n, \u00FF 等）
  • integer / number 有自己的子状态机
  • nested object / array 用栈处理
  • required 字段的顺序无关性需要 OR 结构

19.3 Token-level bitmask 的难点

每个 FSM 状态对应"下一步允许哪些 字符"，但模型输出的是 token（多字符）。一个 token 可能：

  • 完全在当前状态内（接受）
  • 跨多个状态（部分匹配 → 推进多步）
  • 不匹配任何路径（reject）

xgrammar 的关键优化：预计算每个 (FSM 状态, token) 的 (是否允许, 推进到的新状态)，存为查找表。这就是为什么编译能慢到 100ms-1s（取决于 vocab × FSM 状态数）。

19.5 实际 toy 例子：vocab 中只有 5 个 token

token idtoken text说明
0{"合并 token，跨多字符
1name—
2":"—
3"}—
4foo—

对于 schema {"type":"object","properties":{"name":{"type":"string"}}}：

FSM 状态允许的 tokenbitmask (5 bit)
S0 初始{0}0b00001
S1 期待 key{1}0b00010
S2 期待 ":"{2}0b00100
S3 期待 string value{4}0b10000
S4 期待 "}{3}0b01000

采样过程：

  1. S0 → bitmask=0b00001 → 模型只能选 token 0 → 推进到 S1
  2. S1 → bitmask=0b00010 → 选 token 1 → 推进到 S2
  3. S2 → bitmask=0b00100 → 选 token 2 → 推进到 S3
  4. S3 → bitmask=0b10000 → 选 token 4 → 推进到 S4
  5. S4 → bitmask=0b01000 → 选 token 3 → 终止

最终输出：{"name":"foo"}。每一步都不需要采样（只有 1 个允许 token，logits 中其他位置都是 -inf）。

19.6 这解释了为什么结构化输出"加速"

实际生产中，许多 token 是"被强制"的（bitmask 中只有 1 个 bit 为 1），完全可以跳过 forward 直接吐 token。这是 vLLM v1 的 jump-forward decoding 优化（MindIE 当前未实现，优化点）。

21.2 为什么不需要锁？

  1. GIL 保护：Python 字典操作（_grammar_cache, _request_grammars 的读写）在 GIL 下原子化
  2. 设计上单线程访问：异步路径下只有 forward thread 访问 StructuredOutputManager，主线程不接触
  3. xgrammar matcher 是 per-请求独立：不同 cache_id 的 matcher 完全隔离

21.3 潜在并发风险

⚠️ 风险点

风险 1：xgrammar GrammarCompiler 的线程安全

  • compile_json_schema 在 GIL 下调用 C++，xgrammar 文档未明确说明是否线程安全
  • 当前 cache 是 per-process 单例，编译串行进行 → 不会触发并发

风险 2：未来引入异步编译时

  • 若用 ThreadPoolExecutor 后台编译，多个线程可能并发调用 compile_json_schema
  • 预防：需要在 GrammarBackend 加锁

风险 3：bitmask buffer 的复用

  • _bitmask_buffer 是共享缓冲，下次调用会覆盖
  • 解决：出口 bitmask.copy()（已实现）

24. Bug 模式总结与防御性编码 # v3 新增

24.1 本特性中出现/可能出现的 5 类 bug 模式

模式 1：跨进程 IPC 字段缺失

典型 bug：客户端发了 response_format，但 D 节点 grammar 状态空

原因：proto 字段未序列化（construct_execute_request.cpp 漏写）

防御：

  • 所有 proto 字段必须有 round-trip 测试
  • Python 反序列化后必须 assert 字段非 None
  • 添加 metric: ipc_field_missing_count

模式 2：状态机游标错位（双计数器 bug）

典型 bug：grammar 卡死，所有后续 token 都被 reject

原因：依赖第三方库的内部状态（replay buffer）但未暴露

防御：

  • 双计数器：tried/processed 分离
  • 每次推进打日志（tried 前后值）
  • 在 sync 前 dump replay buffer 状态

模式 3：执行顺序依赖（颠倒后多吐字符）

典型 bug：模型多吐一个 { 或类似

原因：Prefill / Decode 路径执行顺序差异未被代码注释或测试固化

防御：

  • 关键执行顺序写在函数 docstring 里
  • 反例（颠倒后的行为）写在单测里
  • code review 时 checklist 要包含 "顺序敏感"项

模式 4：缓存 key 碰撞 / hash 性能

典型 bug：缓存命中率不正常（应该高的低）

原因：用大对象当 key，hash 慢；或 hash 冲突未处理

防御：

  • 短 key（sha256）+ 抗碰撞校验（双值存储）
  • cache 命中率 metric
  • 定期 dump cache 内容验证

模式 5：异步 / 同步路径行为不一致

典型 bug：同步路径正确，异步路径错；或反之

原因：两条路径独立维护，演进时遗漏一条

防御：

  • 统一入口函数（本特性的 build_and_assign_structured_guided_bitmask）
  • 单测同时跑同步 + 异步
  • code review 时强制审视"另一条路径是否同步修改"

24.2 防御性编码清单

✅ Defensive Programming Checklist
  1. 跨进程数据接收处必须 sanitize（如 _sanitize_replay_tokens）
  2. 共享 buffer 必须出口 copy
  3. per-序列异常不阻塞批次（try/except per-iteration）
  4. 调用第三方 C++ 库必须懒加载 + 失败降级
  5. 关键不变量在代码注释中显式声明
  6. 所有"FIFO/LRU/同步/异步"等设计选择都写在注释或文档
  7. cache 容量上限必须有，避免 OOM
  8. 状态机推进必须双向可验证（tried = N, accepted = M, M ≤ N）
  9. fail-fast 路径要让客户端可观察（独立的 end_reason）
  10. 互斥规则在校验层提前拦截，不要等到运行时

25.3 告警建议

🚨 关键告警
  • P95 编译耗时 > 2s：可能是异常 schema
  • Cache 命中率 < 70%：客户端重复发送相同 schema 但 hash 不同（key 序列化不一致）
  • Reject 率 > 1%：grammar 与模型行为不匹配，需 review schema
  • Suffix search 触发 > 0：PD 分离 token 同步异常
  • Active grammars > 1000：grammar 泄漏，clear_finished_requests 未触发

25.4 容量规划公式

peak_memory = bitmask_buffer_size + grammar_cache_size + active_grammars

bitmask_buffer_size = max_concurrent_requests * vocab_size / 8     # 单 rank
grammar_cache_size  = grammar_cache_capacity * avg_compiled_size   # 100 * ~1MB
active_grammars     = max_concurrent_requests * avg_matcher_size   # ~few KB

总计典型: 几十 MB ~ 几百 MB
