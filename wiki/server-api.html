服务端与 API

本章覆盖 src/server/ 全部内容：守护进程的启动流程、 config.json 字段、对外 RESTful / gRPC 接口矩阵，以及 HTTPS 与认证选项。

守护进程：mindie_llm_server

入口文件 src/server/daemon/llm_daemon.cpp。启动顺序：

  1. 解析命令行 / 环境变量：识别 --config、 MINDIE_LOG_TO_STDOUT、ASCEND_RT_VISIBLE_DEVICES 等。
  2. 加载 config.json：通过 config_manager_impl 反序列化为 ServerConfig / BackendConfig 等结构体。
  3. 校验：param_checker.cpp 检查路径权限、字段取值范围、卡数 与 worldSize 的一致性。
  4. 初始化日志 / 加密 / 共享内存 / id 生成。
  5. 构造 LLM Manager，按需启动 worker 子进程。
  6. 拉起 endpoint：注册各协议路由 → 启动 HTTP server → 启动 gRPC server → 健康探针就绪。
  7. 打印 Daemon start success!，进入主循环。

多机部署：ranktable

对应 src/config_manager/ranktable_config.cpp。多机推理时， npuDeviceIds 字段失效，每节点的可用 NPU 由 ranktable 文件描述。 ranktable 是 JSON，记录每张卡的 IP、host id、device id、rank、并行通信组归属， 详见官方 mkdocs 中的「rank table file 配置」。

Endpoint 模块

路径 src/server/endpoint/。组件构成：

  • endpoint.cpp：注册中心，把 URL 路径绑定到具体 handler。
  • http_wrapper/：HTTP/1.1 与 HTTP/2 服务端封装， 基于 Boost.Asio / Boost.Beast。
  • grpc_wrapper/：gRPC 服务端，承担 Triton / 自研 protobuf 通信。
  • health_checker/：实现 /health、 /v2/health/... 探针。
  • single_llm_req_handler/：单请求生命周期 — 校验、 生成 id、入队、流式回写。
  • single_req_infer_interface/：与 LLM Manager 的对接接口。
  • endpoint_def.*：定义可路由的全部端点常量。
  • utils/：URL 解析、JSON 转换、错误码映射等。

HTTPS 与安全

  • 启用 HTTPS：在 ServerConfig 中 httpsEnabled=true 并配置 tlsCa/Cert/Key。
  • 双向认证：interNodeTLSEnabled 控制节点间 mTLS。
  • 密钥保护：src/utils/ 内的加密工具与 OpenSSL 集成， 证书 / 私钥文件需 600 权限。
  • 权限校验：服务进程对权重目录的属主与权限进行严格校验， 失败将直接拒启动。
⚠ 关闭 HTTPS 的风险

当 httpsEnabled=false、未做网络隔离时，请求体（含可能的敏感 prompt） 和模型输出在传输过程中可被嗅探。生产环境务必启用 HTTPS，或部署在私网/内网网关后。

监控指标

/metrics 提供 Prometheus 格式输出，/metrics-json 提供 JSON。 关键指标：

  • ttft_avg / tbt_avg：滚动 1000 个请求的 TTFT / TBT 平均值。
  • 正在执行 / 正在等待请求数。
  • NPU block 剩余数（结合 block_manager 计算）。
  • Prefix Cache 命中率。
