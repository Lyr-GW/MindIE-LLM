常见问题（FAQ）

本章汇总从源码与官方文档中提炼的常见坑点与解决方案。如未列出， 可通过 Issues 反馈。

安装与环境

npu-smi 报错或不存在

  • NPU 驱动未装 / 未启动 → 按硬件型号安装对应驱动固件。
  • 容器中找不到 npu-smi → 检查 docker run 是否挂载了 /usr/local/bin/npu-smi 与 /usr/local/Ascend/driver。
  • 挂载权限不足 → --device=...:rwm 而非 :rw。

提示找不到 CANN / ATB 库

source /usr/local/Ascend/cann/set_env.sh
source /usr/local/Ascend/nnal/atb/set_env.sh
source /usr/local/Ascend/mindie/set_env.sh
echo $LD_LIBRARY_PATH | tr ':' '\n' | grep -E 'cann|atb|mindie'

三个 set_env.sh 必须按顺序 source；缺一不可。

老版本 MindIE 干扰

动态链接器优先解析到老版本，启动直接失败。在升级前重命名旧目录：

mv /usr/local/Ascend/mindie /usr/local/Ascend/mindie-bak

配置与启动

config.json 权限错误

必须 640 权限，否则启动失败：

chmod 640 mindie_llm/conf/config.json

权重目录权限

MindIE-LLM 对权重目录做严格属主 / 权限校验。建议：

chmod -R 755 /home/weight     # 目录
find /home/weight -type f -exec chmod 640 {} \;   # 文件
chown -R $(id -u):$(id -g) /home/weight

worldSize 与 npuDeviceIds 不一致

worldSize 必须等于每实例使用的卡数，即 npuDeviceIds[i] 的长度。 不一致会在 param_checker 阶段直接报错。

ASCEND_RT_VISIBLE_DEVICES 影响逻辑 ID

设置该变量后，可见卡的逻辑 ID 从 0 开始重新计数。 npuDeviceIds 应使用重新映射后的 ID。例：

export ASCEND_RT_VISIBLE_DEVICES=1,2,3,4
# 此时 npuDeviceIds 写 [[0,1,2,3]] 即可，对应物理卡 1,2,3,4

运行时

kernel_meta 写权限错误

CANN 在「执行目录」会生成 kernel_meta_temp_xxxx 与 kernel_meta。 bin/ 目录通常 550 无写权限，需要换到可写目录启动。

cd $HOME/work_dir       # 任一可写目录
mindie_llm_server

切换用户后启动失败

共享内存文件遗留导致权限冲突，先清理再启动：

rm -f /dev/shm/*
mindie_llm_server

OOM / KV blocks 不足

  • 调小 maxBatchSize / maxPrefillBatchSize / maxPrefillTokens。
  • 调小 maxSeqLen。
  • 启用 KV Cache 池化 把冷 KV 下放到 CPU。
  • 启用 KV Cache Int8 把 KV 显存压缩一半。

关闭 HTTPS 的安全提示

启动日志会反复提醒 httpsEnabled=false 的风险。生产环境必须开启 HTTPS 并配置 TLS 证书。仅在受控内网做调试时可临时关闭。

流式接口看不到流

  • 客户端需要使用 Accept: text/event-stream 或显式带 "stream": true 字段。
  • 有些代理 / 网关会缓冲响应；测试时直接访问服务 IP。
  • 调用 /generate_stream 而不是 /generate。

输出突然截断

  • 命中 max_new_tokens 上限。
  • 命中 maxIterTimes（服务端硬上限）。
  • 命中 EOS token。如需忽略 EOS，传 "ignore_eos": true。
  • 结构化输出场景中 schema 不允许更多 token。

模型适配

是否启用 trustRemoteCode

权重目录里若包含 modeling_*.py 等远程代码（HuggingFace 风格）， 启用后 MindIE 会执行这些代码 — 存在代码注入风险。 建议：

  • 仅在自家可信权重上启用。
  • 第三方权重务必先审计代码，或用 ATB Models 的内置实现绕开。

提示模型不被支持

  • 查 代码仓模型支持列表。
  • 若是新模型 → 参考 docs/zh/developer_guide/migration_and_adaptation_guide。
  • 多模态理解类需走专门迁移指南。

性能调优

吞吐不达预期

  • 检查是否打开 Continuous Batching（默认开），maxBatchSize 是否过小。
  • 启用 异步调度。
  • 启用 SplitFuse 让 prefill 与 decode 同 step。
  • 启用合适的 量化。
  • 评估并行策略是否合理（TP 太大可能反伤吞吐）。

TTFT 高

  • 启用 Prefix Cache。
  • 长 prompt 启用 Context Parallel。
  • 检查队列等待 — 调大 maxPrefillBatchSize。

TPOT 高

  • 启用 MTP / 投机解码。
  • 把 KV 量化到 int8 释放更多 batch 空间。
  • MoE 模型启用 EPLB / 共享专家外置。

多机多卡

ranktable 配置

  • 所有节点的 ranktable JSON 必须一致；rank id 全局唯一。
  • HCCL 通信端口需在防火墙放行。
  • 多机模式下 npuDeviceIds 字段失效，由 ranktable 决定。

HCCL 通信报错

  • 检查节点间网络可达；推荐 RDMA / RoCE。
  • 设 HCCL_DEBUG=INFO 查看具体阶段失败。
  • 所有节点的 CANN / ATB / MindIE 版本必须严格一致。

日志与排障

日志在哪

  • 设 MINDIE_LOG_TO_STDOUT=1 → 直接打到当前终端。
  • 否则按 LogConfig 中的路径滚动落盘。
  • 关键关键字：Daemon start success!、scheduler.policy、 block_manager、endpoint。

如何打开调试日志

export MINDIE_LLM_LOG_LEVEL=DEBUG
export HCCL_DEBUG=INFO
mindie_llm_server
