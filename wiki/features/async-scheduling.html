异步调度

让 CPU 上的请求调度 / 数据准备 / 结果回收与 NPU 上的 模型推理并行执行。一个简单的多线程改造，可在大 batch、长输出场景下 把 CPU 时间「藏到」NPU 计算之后，吞吐显著提升。

问题：CPU/NPU 串行

同步推理流水：

   时间 →
   CPU:  [调度 准备] ─────────── [回收 响应] [调度 准备] ─── ...
   NPU:               [推理 + 采样]                          [推理 + 采样]
              ↑           ↑                ↑
            CPU 等 NPU    NPU 算           NPU 等 CPU

每一轮中 CPU、NPU 都有空闲段。Batch 越大、输出越长，调度准备 / 结果回收 的绝对时间越长，浪费越严重。

异步思路

   时间 →
   CPU:  [调度 N+0] [回收 N-1] [调度 N+1] [回收 N+0] [调度 N+2] [回收 N+1] ...
   NPU:           [推理 N+0]            [推理 N+1]             [推理 N+2]
  • 双 buffer + 多线程：当 NPU 在算 N，CPU 已经在为 N+1 准备数据， 同时为 N-1 做后处理。
  • 调度领先 NPU 一轮：通过 maxScheduledBatch_ = 2 实现「异步单发」。
  • EOS 重算代价：已进入 EOS 状态的请求会被多算 1 轮， 浪费 NPU 显存和算力的小额成本。

如何开启

# 1. 设置环境变量（D 节点开启）
export MINDIE_ASYNC_SCHEDULING_ENABLE=1

# 2. 启动服务
mindie_llm_server
📌 PD 分离

仅在 D 节点开启异步调度；P 节点不需要。

在调度器中的体现

src/scheduler/scheduler.h 中：

// 调度实际下发的批次：同步=1，异步（异步单发）=2
size_t maxScheduledBatch_{1};

异步打开后，调度循环允许提前计划下一轮 batch；执行器线程在 NPU 完成当前轮后立即拉走预备好的下一轮。

什么时候收益最大

  • 大 maxBatchSize（≥ 64）：CPU 端处理量随 batch 线性涨。
  • 长输出：每轮 decode 时间相对短，CPU 端反而变成瓶颈。
  • 多 token 后处理（结构化输出 / Function Call）：CPU 计算密集时收益尤其大。

已知限制

  • 支持 PD 混部、PD 分离场景。
  • 不能与 Lookahead、Memory Decoding 同时开启。
  • 暂不支持 n、best_of、use_beam_search 等多序列后处理参数。

收益

  • 典型场景吞吐 +10–25%。
  • 对小 batch / 短输出收益有限，甚至可能因 EOS 重算反而降低。
