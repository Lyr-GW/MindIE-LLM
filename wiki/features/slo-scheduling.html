SLO 调度优化

在确保 SLO（TTFT / TPOT 时延目标）的前提下最大化吞吐。 MindIE-LLM 提供两个互补算法：基于 LLF 的 PD 阶段选择，与基于 TPOT 的动态 BatchSize 调整。

问题：高并发下的 SLO 与吞吐冲突

  • 盲目堆高 batch → 吞吐高、但 TTFT/TPOT 可能超阈。
  • 限制 batch → SLO 稳、但资源浪费、吞吐低。

SLO 优化的目标是在两者之间「智能取舍」 — 哪些请求该挤进当前 batch、哪些该等下一轮。

算法 ①：LLF（Least Laxity First）阶段选择

松弛度（laxity）= 剩余可用时间 - 还需多少时间。LLF 把最容易超时 的请求 / 阶段优先安排。流程：

  1. 采集近期 TTFT、TPOT 实测数据 → 用 latency_predictor 的回归模型拟合 prefill / decode 耗时。
  2. 对当前 waiting / running 请求计算各自的 laxity。
  3. 选择 laxity 最小的阶段（可能是某个 P，也可能是某个 D 群）下发。

适合 TTFT、TPOT 都有严格阈值的场景。

算法 ②：动态 BatchSize 调整

持续监测 TPOT，与 SLO 目标比较：

  • TPOT 接近上限 → 缩小 maxPrefillBatchSize / maxBatchSize， 避免拥塞；
  • TPOT 远低于上限 → 缓慢扩大 batch，挖掘吞吐。

注意：TPOT 监测有 ~10% 波动，最终落点可能与配置目标偏差 10%。

配置

"ScheduleConfig": {
  "stageSelectPolicy":      2,        // 0 prefill 优先 / 1 吞吐优先 / 2 LLF
  "dynamicBatchSizeEnable": true,     // 算法 ② 开关
  "prefillExpectedTime":    1000,     // ms，TTFT SLO
  "decodeExpectedTime":     50        // ms，TPOT SLO
}

在调度器中的实现

  • LLF：scheduler/scheduler.cpp 中的 DecidePDPriority + latency_predictor。
  • 动态 BatchSize：scheduler/policy/dynamic_batch_size.cpp + dynamic_batch_recorder.cpp，滑动窗口记录最近 N 轮的 batch / 延迟，下一轮自适应。

收益

  • 短输出（< 256 token）场景吞吐 +10–30%，且 SLO 达成率 ↑。
  • 长输出场景收益减小（单步耗时主导），需结合 KV 量化 / 投机解码进一步优化。

已知限制

  • 仅 Atlas 800I A2 推理服务器支持。
  • DeepSeek-R1 / V3、Qwen 系列支持。
  • 仅适用于 PD 混部场景；不能与 SplitFuse 同开。
  • 主要收益在短输出场景；输出越长，吞吐增益越小。
