并行策略

从单卡跑不动 13B，到 8 卡跑通 70B，再到几十节点上承载万亿 MoE， MindIE-LLM 通过 TP / DP / EP / CP / SP 五种并行 方式自由组合，应对不同规模与场景。

五种并行总览

   并行         切分对象          通信      典型用途
   ──────────  ──────────────  ────────  ──────────────────
   TP (张量)   权重矩阵列/行     AllReduce  单实例多卡
   DP (数据)   batch 维度       梯度无     多实例同模型扩并发
   EP (专家)   MoE 专家         AllToAll   稀疏模型扩参数量
   CP (上下文) 序列 chunk       Ring/SP   超长上下文 prefill
   SP (序列)   序列维度的 KV    All-Gather 长上下文 decode

Tensor Parallel（张量并行）

把模型的权重矩阵在维度上切分到多张卡。

  • 典型实现：Megatron 风格 — Linear 层按 column / row 切分； Attention 按 head 切分。MindIE-LLM 在 runtime/layers/linear 提供 ColumnParallelLinear / RowParallelLinear。
  • 通信：每个 transformer 层若干次 AllReduce， 延迟敏感。
  • 配置：通过 worldSize 控制；同一 npuDeviceIds 集合下所有卡是同一个 TP 组。
  • 适用：单模型显存放不下时的首选。

Data Parallel（数据并行）

把不同请求 / 批次分配到不同设备组，每组独立完成 forward。

  • 等价于多实例同模型，请求级横向扩展。
  • 通信：推理阶段几乎无组间通信。
  • 配置：npuDeviceIds 写成多组，例如 [[0,1,2,3],[4,5,6,7]] 表示两个 DP 实例，每实例 4 卡 TP。
  • 价值：吞吐线性扩展。

Expert Parallel（专家并行）

仅在 MoE 模型中存在：把不同专家分布到不同卡。

  • 通信：每个 token 在 routing 后通过 AllToAll 送到目标专家所在卡。
  • 挑战：专家间负载不均衡 — 某些专家被频繁选中。
  • 缓解方案：
    • 负载均衡（Expert Parallelism Load Balancer，EPLB）
    • 共享专家外置（独立部署高频共享专家）
  • 配置：pluginParams.expert_parallel.enable=true + 路由策略参数。

负载均衡（EPLB）

通过：

  1. 线上统计各专家访问频率（runtime 中 EP 模块负责采集）。
  2. 动态冗余复制热门专家到其他卡，使路由可分流。
  3. 定期再平衡，避免长时间倾斜。

共享专家外置

MoE 中常有「共享专家」（如 DeepSeek 的 shared experts），所有 token 都会经过。 把它独立部署到专卡，与路由专家分离：

  • 共享专家所在卡可全力做密集计算，不参与 AllToAll。
  • 路由专家所在卡专注稀疏路由。
  • 整体 TPOT 显著改善。

Context Parallel（上下文并行）

专为长 prompt prefill 设计：把 prompt 的 token 序列在 上下文维度切分到多卡，每卡只算一段，再通过 ring / 序列通信完成 attention 的全局交互。

  • 价值：减小单卡 prefill 时长，降低首 token 时延。
  • 通信：环状传 K / V。
  • 典型场景：上下文 128k+ 的长文档。

Sequence Parallel（序列并行）

侧重 decode 阶段：把 KV Cache 按序列长度切分，每张卡持有 不同片段的 KV，本地计算 + AllGather 合并。

  • 价值：当 KV 太大单卡装不下时的关键手段。
  • 组合：常与 CP 同时启用，覆盖长 prefill + 长 decode。

组合矩阵

组合含义注意
TP × DP单实例多卡 × 多实例最常见，npuDeviceIds 二维数组直接表达
TP × EP稠密层 TP，专家层 EPMoE 模型常用
TP × CP长 prompt prefill 加速同一组卡同时承担 TP 与 CP
TP × SP长上下文 decode切 KV，需更高带宽
EP × DP多 MoE 实例注意 EPLB 同步策略
TP × CP × SP极致长上下文对网络拓扑要求高

多机部署：ranktable

多机推理时用 ranktable JSON 描述全局拓扑，由 config_manager/ranktable_config.cpp 解析。 ranktable 至少包含：

  • server_list：各节点 IP / device list / rank id。
  • parallel_group：每张卡所在的 TP / DP / EP 组。
  • communication_backend：HCCL 等。

启动时把 ranktable 路径写入 config.json，npuDeviceIds 字段在多机模式下被忽略，节点上的卡集合由 ranktable 决定。

典型配置

8 卡：TP=4 + DP=2

"BackendConfig": {
  "npuDeviceIds": [[0,1,2,3], [4,5,6,7]],
  "ModelDeployConfig": {
    "ModelConfig": [{
      "modelName": "llama2-70b",
      "modelWeightPath": "/home/weight",
      "worldSize": 4
    }]
  }
}

MoE 模型：TP=2 + EP=4

"BackendConfig": {
  "npuDeviceIds": [[0,1,2,3,4,5,6,7]],
  "ModelDeployConfig": {
    "ModelConfig": [{
      "modelName": "deepseek-moe",
      "modelWeightPath": "/home/weight",
      "worldSize": 8,
      "pluginParams": {
        "tensor_parallel_size": 2,
        "expert_parallel_size": 4,
        "expert_parallel_load_balance": true,
        "shared_expert_external": true
      }
    }]
  }
}

长上下文：TP=4 + CP=2

"BackendConfig": {
  "npuDeviceIds": [[0,1,2,3,4,5,6,7]],
  "ModelDeployConfig": {
    "ModelConfig": [{
      "modelName": "qwen2-72b-128k",

调优要点

  • 把 HCCL 通信日志打开（HCCL_DEBUG=INFO），观察 AllReduce / AllToAll 是否成为瓶颈。
  • TP 越大单步越慢、batch 越能塞大；DP 越大并发越高、单 batch 不变。
  • MoE 启用 EPLB 时关注热点专家分布，必要时调整 routing 平滑因子。
  • CP / SP 受限于网络，如果是单机内多卡可优先 CP；跨机谨慎评估。
