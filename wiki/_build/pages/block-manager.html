KV Cache 与 Block Manager

大模型推理的显存瓶颈几乎全集中在 KV Cache 上。MindIE-LLM 的 src/block_manager/ 实现了一套完整的「分块 + 引用计数 + LRU 驱逐 + Copy-on-Write + 异构存储」KV 管理方案。

为什么需要 Block Manager

朴素实现会给每个序列预留「最大长度 × 头数 × 维度」的连续显存，导致：

  • 显存浪费：长上下文导致大量 padding 不被使用。
  • 无法共享：相同 prompt 的多个请求重复计算 KV。
  • 无法弹性：突发长请求需要中断或拒绝。

PagedAttention 的核心思想是：把 KV 切成固定大小的「块」（block），每个序列持有一张 block 表（page table）。MindIE-LLM 在此基础上叠加了 prefix cache、CoW、CPU 池化等优化。

顶层管理器

  • SelfAttnBlockManager （self_attn_block_manager.cpp/h）：标准 self-attention 模型的 KV 管理器。 负责为每个请求建立 BlockTable，并在调度器请求时申请 / 释放 block。
  • LwdSelfAttnBlockManager （lwd_self_attn_block_manager.cpp/h）：Layerwise Decode 优化版本， 与 LayerwiseFCFS 调度策略配合， 支持 layer 粒度的混合执行。
  • RequestSingleBlockManager （request_single_block_manager.cpp/h）：单请求专用管理器，简化场景使用。

分配器矩阵

所有分配器共享 DeviceAwareBlockAllocator（device_aware_block_allocator.h） 接口，由顶层根据配置选择具体实现。

HashlessBlockAllocator

文件：hashless_block_allocator.cpp/h + hashless_block_obj.cpp/h。

  • 最基础的 free-list 分配器：维护一个全局空闲池，O(1) 分配 / 释放。
  • 不做任何前缀复用，适合 prefix cache 关闭或命中率低的场景。
  • 典型搭配 LRUEvictor 做被动驱逐。

PrefixCacheBlockAllocator

文件：prefix_cache_block_allocator.cpp/h + prefix_cache_block.cpp/h。

  • 每个 block 计算 hash（包含 token id 序列与父 block hash），相同前缀的多个请求 共享 block。
  • 命中率统计由 HitRateCalculator 维护，输出到 /metrics。
  • 命中后省去 prefill 计算，TTFT 显著降低。
  • 对应 加速特性 → Prefix Cache。

CpuNpuBlockAllocator

文件：cpu_npu_block_allocator.cpp/h。

  • 实现两级存储：NPU 上是热数据，CPU DRAM（甚至 SSD via mmap）是冷数据。
  • 当 NPU 空间紧张，把最久未访问的 block swap 到 CPU；命中时再 swap 回 NPU。
  • 对应 加速特性 → KV Cache 池化。

驱逐策略

接口 evictor.h，目前主要实现 LRUEvictor （lru_evictor.cpp/h）：

  • 按访问时间组织一个双向链表，最新访问移到表尾，驱逐时取表头。
  • 对 prefix cache 友好：被多请求共享的 block 引用计数高，自然不会被驱逐。

引用计数

文件 ref_counter.cpp/h + ref_counter_protocol.h。

  • 每个 block 都附带 RefCount。命中 prefix cache 时 +1，请求结束时 −1。
  • 引用计数为 0 才能进入驱逐候选；为 0 且未分裂的可以直接回收。
  • 避免共享 block 被错误释放。

Copy-on-Write

文件 copy_on_write_tracker.cpp/h。

当多个序列共享同一个 prefix block，但其中一个序列要在该 block 内追加新 token（变得不同） 时，需要 CoW 复制该 block 的内容并把当前序列的 BlockTable 指向新 block， 其他共享者继续使用旧 block。Tracker 负责：

  • 识别 fork point，记录 CoW 事件。
  • 触发新 block 申请 + 内容拷贝。
  • 更新引用计数。

命中率统计

文件 hit_rate_calculator.cpp/h。

  • 滑动窗口统计请求级 / token 级命中率。
  • 对外通过 /metrics、/metrics-json 暴露。
  • 用于评估 prefix cache 是否值得开启（命中率持续低 5% 时建议关闭）。

辅助结构

  • BlockTable（block_table.cpp/h）： 每序列的 page table，记录 token → block 索引映射。
  • BlockTracker（block_tracker.cpp/h）： 全局 block 状态跟踪（被哪些序列持有、引用计数、CoW 状态）。
  • ObjPool（obj_pool.h）：通用对象池， Block 对象避免频繁 new/delete。
  • BlockObj（block_obj.h）：block 对象封装。

一次分配生命周期

  1. 请求到来：调度器决定可纳入本轮 batch，向 BlockManager 请求 N 个 block（基于 prompt 长度）。
  2. 查 prefix cache：PrefixCacheBlockAllocator 计算 hash，逐 block 比对。命中前缀 K 个 block 直接复用并 +1 引用。
  3. 申请新 block：剩余 N−K 个 block 走自由池或触发 LRU 驱逐。
  4. 建表：写入该序列的 BlockTable，发回调度器。
  5. token 增长：每次新 token，写入当前 block； block 写满则申请下一个。
  6. 序列结束 / 中止：遍历 BlockTable，对每个 block 引用计数 −1； 归 0 进入驱逐候选。
  7. 共享分裂：若某 block 被 fork，CoWTracker 触发复制并改写表项。

问题排查

  • 显存 OOM 报错 → 减小 maxBatchSize 或 maxPrefillTokens。
  • Prefix Cache 命中率低 → 检查请求模板是否包含变量前缀（如时间戳），把变量后置。
  • Swap 抖动 → CPU pool 太小或访问局部性差，调大 cpuMemSize。
  • 引用计数泄漏 → 主要发生在异常请求中断路径；可在 HitRateCalculator 与 BlockTracker 加日志辅助定位。
