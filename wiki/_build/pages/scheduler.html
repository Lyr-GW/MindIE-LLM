调度器

调度器决定 哪些请求 在 哪一轮 以 什么 batch 进入推理 — 是 LLM 推理服务吞吐 / 时延 / SLO 达成率的中枢。本章把 src/scheduler/ 整个目录从「请求队列」到「策略 / 时延预测器 / Preempt」全部讲清楚，并附关键源码片段。

1. 调度要回答的四个问题

  1. 什么时候进入推理？新到达的请求进等待队列，组什么样的 batch 再下发？
  2. 谁优先？FCFS、PDDS、Layerwise 等策略有什么差别？
  3. 显存够不够？每轮组 batch 都要问 block_manager。
  4. SLO 风险吗？如果加入这个请求会让在飞请求超时怎么办？

2. 三个并发队列 + 一张 transferring 表

看 src/scheduler/scheduler.h 中 Scheduler 类成员：

// 摘自 scheduler.h（精简注释）
ConcurrentDeque<SequenceGroupSPtr> waiting_;     // 待 prefill / 待拉 KV 的请求
ConcurrentDeque<SequenceGroupSPtr> running_;     // 已分到 KV、正在 decode 的请求
ConcurrentDeque<SequenceGroupSPtr> swapped_;     // KV 被换到 CPU 的请求
ConcurrentMap<SequenceId, SequenceGroupSPtr> transferringMap_;  // 正在跨节点拉 KV

「一切请求都在某个队列里」是理解调度器的第一原则。Scheduler::Schedule() 每轮做的事：把 waiting / running / swapped 的当前快照 喂给策略，由策略决定本轮 batch；原始队列仍是 concurrent，主线程仍能接收新请求。

3. 一轮调度的全景

   ┌────────────────────────────────────────────────────────────────┐
   │ Scheduler::Schedule()                                          │
   │                                                                │
   │  ① DecidePDPriority()  → 决定本轮是 PrefillFirst/DecodeFirst/Mix │
   │                                                                │
   │  ② PrepCandidatesForPolicy()  → 把并发队列拷贝到策略私有 deque    │
   │                                                                │

   │       ├── ApplyToWaitingQueue()    挑可 prefill 的请求          │

   │  ④ BackfillConcurrentQueue()  → 把未选中的请求放回原队列        │
   │                                                                │
   │  ⑤ ConvertToSchedulerOutput() → 给执行器一个可下发的 SchedulerOut │
   │                                                                │
   │  ⑥ RecordMetricsStatics()    → 输出 metrics                    │
   └────────────────────────────────────────────────────────────────┘

4. SchedulingBudget — 本轮的「钱包」

预算决定本轮最多吃多少 token / 多少 seq。看 src/sequence/scheduling_budget.cpp：

// 精简自 SchedulingBudget
class SchedulingBudget {
    size_t maxNumSeqs_;                  // ≤ maxBatchSize
    size_t maxNumBatchedTokens_;         // ≤ maxPrefillTokens
    size_t numCurSeqs_       = 0;
    size_t numBatchedTokens_ = 0;

    bool CanSchedule(size_t newTokens, size_t newSeqs) const {
        return numBatchedTokens_ + newTokens <= maxNumBatchedTokens_
            && numCurSeqs_      + newSeqs   <= maxNumSeqs_;
    }
    void AddNumBatchedTokens(RequestId& r, size_t n, size_t cached);
    void AddNumSeqs        (RequestId& r, size_t n);
};

策略在挑请求时会反复问 budget.CanSchedule(...)，命中即停。 Chunked Prefill 模式下 budget 还会维护 partialPrefillOccupiedBudgetPerSlot_：动态决定每个并发 prefill 占多少 token 配额，避免长 prompt 把整轮配额吃光。

5. 策略统一接口

src/scheduler/policy/policy.h 定义全部策略要实现的接口：

// 摘自 policy.h（精简）
struct PolicyOutput {
    std::deque<SequenceGroupSPtr>            withdrewSeqGroups_;     // 退回原队列
    std::vector<SequenceGroupSPtr>           preemptedSeqGroups_;   // 被驱逐
    std::vector<ScheduledSequenceGroupSPtr>  prefillSeqGroups_;     // 本轮 prefill
    std::vector<ScheduledSequenceGroupSPtr>  decodeSeqGroups_;      // 本轮 decode
    std::vector<SequenceGroupSPtr>           swappedOutSeqGroups_;
    std::vector<SequenceGroupSPtr>           ignoredSeqGroups_;     // 永远拒绝
    std::vector<std::pair<BlockId,BlockId>>  blocksToSwapIn_;
    std::vector<std::pair<BlockId,BlockId>>  blocksToSwapOut_;
    std::vector<std::pair<BlockId,BlockId>>  blocksToCopy_;          // CoW
    size_t numPrefillGroups{0}, numBatchedTokens{0}, numPreempted{0};
};

class Policy {
public:
    virtual PolicyOutput Apply(SchedulingBudget& budget,
                               std::shared_ptr<SeqGroupCollection>& collection) = 0;
    bool newRequestFirst_{false};
};

策略输出不是 raw token，而是「哪些 seq group 进 batch、哪些 KV block 要 swap / copy」 这种调度层语义；后续由 Scheduler::ConvertToSchedulerOutput() 翻译为执行器 消费的格式。

6. FcfsPolicy — 最常用的实现

scheduler/policy/fcfs_policy.cpp 是「First-Come-First-Serve」 的实现，但不是简单 FIFO。它根据 pdPriorityType 切换三种调度模式：

// 精简自 FcfsPolicy::Apply
PolicyOutput FcfsPolicy::Apply(SchedulingBudget& budget, ISeqGroupCollectionSPtr& collection) {
    PreprocessCollection(collection);
    switch (collection->pdPriorityType_) {
        case PDPriorityType::PREFILL_FIRST: return SchedulePrefill(budget);
        case PDPriorityType::DECODE_FIRST:  return ScheduleDecode(budget);
        case PDPriorityType::MIX:           return ScheduleChunkedPrefill(budget);
        default: throw std::runtime_error("...");
    }
}

三种模式的差异：

  • PREFILL_FIRST：只动 waiting 队列，做整段 prefill。决策最简单， 适合纯 prefill 实例（PD 分离的 P 端）。
  • DECODE_FIRST：先动 running 队列把 decode 排满；只有当 running 没有发生 preempt / swap 时，才尝试 swap-in。适合 D 端。
  • MIX（chunked prefill）：先动 running，再动 waiting； 先生成 Statistics4PartialPrefill 决定可同时进行的 partial prefill 数量， 做到「decode 与 chunk-prefill 同 step 执行」。

7. PDDSPolicy — PD 分离场景

policy/pdds_policy.cpp 继承自 FcfsPolicy， 根据本实例 角色（P/D）选择路径：

// 精简自 PDDSPolicy::Apply
PolicyOutput PDDSPolicy::Apply(SchedulingBudget& budget, std::shared_ptr<SeqGroupCollection>& col) {
    PreprocessCollection(col);
    switch (role_) {
        case Role::P:
            if (schedulerConfig_->enableChunkedPrefill) return ScheduleChunkedPrefill(budget);
            return SchedulePrefill(budget);
        case Role::D:
            return ScheduleDecode(budget);
        default: throw std::runtime_error("...");
    }
}

同一个仓库还在该文件里实现了 KVTransferSchedulePolicy — D 端用来从 P 端 拉 KV 的调度策略。它做的事情：

  1. 从 waiting 队列取 seqGroup；
  2. 检查 NPU 还剩多少 free block，预留 PRESERVED_FACTOR_FOR_DECODE × totalBlocks 给 decode；
  3. 调用 blockManager_->CanAllocate 决定 OK / LATER / NEVER；
  4. 调用 budget.CanSchedule 终判；
  5. 分配 KV，把请求放入 pullSeqGroups 准备从 P 端拉 KV。

8. LayerwiseFCFS — 把 forward 切到 layer 粒度

常规调度以「整个 model.forward()」为最小执行单元；layerwise 调度则把每一层都拿出来 和别的请求混排：

   传统：[ Req1 prefill 30 layer ][ Req2 decode 30 layer ][ Req3 decode 30 layer ]
   LWD ：[ R1.L0 R2.L0 R3.L0 ][ R1.L1 R2.L1 R3.L1 ] … 同步推进

带来的好处：

  • 长 prompt 不再阻塞短请求；
  • 跨请求的 layer-by-layer 可调度更细，配合 LWD 专用 block manager 减少显存高峰。

实现侧由 LayerwiseFcfsPolicy + LwdSelfAttnBlockManager + LayerwiseMixin（cpp-engine）三方共同构成。

9. 时延预测器 — SLO 调度的眼睛

看 scheduler/latency_predictor/latency_predictor.cpp：

// 精简自 LatencyPredictor
void LatencyPredictor::UpdateBatchStats() {
    // 每轮调度结束后，把 batch 的实际执行时长喂给回归器
    BatchStatsPtr s = batchStatsMap_.Get(batchId_).value();
    s->batchSpendTimeFloat = duration_cast<ms>(now - s->batchStartTime).count();
    if (s->forwardMode == ForwardMode::PREFILL) {
        prefillRegression_.AddDataPoint(s->numBatchedTokens, s->batchSpendTimeFloat);
        prefillLatency_.AddDataPoint(s->batchSpendTimeFloat);
    } else {
        decodeRegression_.AddDataPoint(s->numBatchedTokens, s->kvCacheBlockNum,
                                       s->batchSpendTimeFloat);
    }
}

float LatencyPredictor::PredictBatchExecTime(BatchStats& s) {
    if (s.forwardMode == ForwardMode::PREFILL)
        return prefillRegression_.Predict(s.numBatchedTokens);
    return decodeRegression_.Predict(s.numBatchedTokens, s.kvCacheBlockNum);
}

三个组件协作：

  • prefillRegression_ — 输入 (token 数) → 输出 prefill 耗时。
  • decodeRegression_ — 输入 (batch 大小, KV block 数) → 输出 decode 耗时。
  • prefillLatency_ / decodeLatency_ — 滑动窗口百分位统计，用来看 P50/P99。

有了它，调度器在「为吞吐组更大 batch」与「为 SLO 让一部分请求等下一轮」之间就能做加权决策。

10. 抢占（Preemption）：当显存不够

看 scheduler.h：

enum class PreemptionMode : int { NONE = 0, SWAP, RECOMPUTE };
  • RECOMPUTE：把序列从 running 移回 waiting，KV 直接释放；下次重新 prefill。
  • SWAP：把序列 KV 从 NPU 搬到 CPU（需 CpuNpuBlockAllocator）， 状态进入 swapped_；条件成熟再 swap-in。

maxPreemptCount 限制每轮最多抢占次数，避免抖动。

13. 扩展：实现你自己的策略

  1. 在 scheduler/policy/ 新建 my_policy.cpp/h，继承 Policy；
  2. 实现 Apply()，按需复用 FcfsPolicy::ApplyToWaitingQueue 等 底层方法，或直接重写；
  3. 在 policy_factory.cpp 增加根据 ScheduleConfig.templateType="MyPolicy" 的实例化分支；
  4. 用 SchedulingBudget 控制 token / seq 上限；
  5. 对外暴露：选择性地把策略相关指标加入 SchedulerMetricsStatics；
  6. 在 tests/dlt/scheduler/ 加单测。
