调度器

调度器是 MindIE-LLM 的「请求大脑」。它决定 哪些请求 在 哪一轮 以 什么 batch 进入推理 — 直接决定 TTFT、TPOT、整体吞吐与 SLO 达成率。 本章拆解 src/scheduler/ 全部组件。

调度目标

对一个 LLM 推理服务来说，「好调度」需要同时兼顾：

  • 吞吐：在 NPU 算力 / 显存允许的前提下尽量组大 batch。
  • 时延：保证已开始的请求按 SLO 完成（TTFT / TPOT 不超阈值）。
  • 公平：避免长请求把短请求饿死。
  • 资源约束：KV block、跨卡通信、batch 内 padding 等的硬上限。

两阶段：pre / post scheduler

  • pre_scheduler.cpp：在调度循环开始前，把 新到达的请求纳入等待队列，做基础校验（最大长度、参数合法性、是否启用 prefix cache 等）。它不做选择，只做「准入」。
  • scheduler.cpp：本轮真正的调度，把候选 SeqGroup 经过策略 排序后按预算装入 batch。
  • post_scheduler.cpp：选完之后做「事后评估」 — 是否触发 Preempt（驱逐）、是否需要 swap KV block、是否需要分裂 prefill。

策略族：scheduler/policy/

策略文件核心思想典型场景
FCFS fcfs_policy.cpp 先到先服务，最朴素 无 SLO 压力的均质负载
PDDS pdds_policy.cpp Prefill–Decode Disaggregated Scheduling，按阶段分别打分； decode 优先以保 TPOT，prefill 灵活组合以保 TTFT 长尾请求多、SLO 严格
LayerwiseFCFS layerwise_fcfs_policy.cpp 把 forward 拆到 layer 粒度，使 prefill / decode 可以在同一 step 中混合执行 长上下文 + 高并发解码
StagePolicy policy/stage_policy/ 面向 Pipeline / 阶段化模型的调度 多阶段流水推理
DynamicBatchSize dynamic_batch_size.cpp + dynamic_batch_recorder.cpp 记录历史 batch 的延迟，自动调整下一轮 batch 上限 负载波动大

策略接口

所有策略实现 policy.h 中的接口（伪代码）：

class IPolicy {
public:
    virtual ~IPolicy() = default;

    // 对当前候选集合按优先级排序
    virtual void Sort(SeqGroupCollection& candidates,
                      const SchedulingBudget& budget) = 0;

    // 是否允许在本轮调度中容纳 sg
    virtual bool CanAdmit(const SequenceGroup& sg,
                          const SchedulingBudget& budget) const = 0;

    // 选完后给上层的 hint（preempt / split 等）
    virtual SchedulingHint OnSelected(const SequenceGroup& sg) = 0;
};

policy_factory.cpp 根据 ScheduleConfig.templateType 与开关 参数（如 supportSelectBatch、splitFuseEnabled）实例化具体策略。

辅助工具

  • policy_helper.cpp：常用工具，如计算请求剩余长度、 预估 KV 占用、判断是否命中 prefix cache 等，避免每个策略各写一遍。
  • seq_group_collection.cpp：候选池抽象，提供按状态、 按 lora_id、按命中率等切片视图。
  • dynamic_batch_recorder.cpp：滑动窗口记录最近 N 轮的 实际 batch 大小与延迟，作为 DynamicBatchSize 的输入。

时延预测：latency_predictor/

SLO 调度优化（详见 加速特性）依赖时延预测器对 「如果把这个请求加入 batch，会不会让在飞请求超时」做出判断。组件：

  • prefill_regression.cpp/h：根据 prefill 长度、batch 大小、 模型规模拟合 prefill 耗时（线性或多项式回归）。
  • decode_regression.cpp/h：拟合 decode 耗时（受 batch 大小、 running KV block 数量影响）。
  • queue_counter.cpp/h：监测当前等待队列长度。
  • batch_latency_tracker.cpp/h：实测每轮 batch 的延迟， 定期更新回归参数。
  • latency_predictor.cpp/h：聚合上述子组件，给调度器 提供 PredictPrefill(...) / PredictDecode(...) 接口。

有了它，调度器就能在「为了吞吐组更大 batch」与「为了 SLO 让一部分请求等下一轮」 之间做加权决策。

Continuous Batching 与 PagedAttention

这两项是 MindIE-LLM 的默认能力，调度器层面体现：

  • Continuous Batching：每一轮 forward 都会重新组 batch； 某个序列结束后立即被新请求填补，不像静态 batch 那样等齐。
  • PagedAttention：调度器与 block_manager 协作 — 在准入阶段先估算「这一轮需要多少 KV block」，不够则拒入或触发驱逐。

SplitFuse / Chunk Prefill 的调度切入

当 splitFuseEnabled=true：

  • 调度器把长 prompt（超过 maxPrefillTokens）拆成多个 chunk。
  • 每一轮可以同时执行：A 请求 chunk-prefill + B 请求 decode。
  • 策略侧由 policy_helper 计算切分点，post_scheduler 标记 哪些请求处于「prefill 中」状态。

驱逐与 Swap

当 KV block 不足以容纳所有 running 请求时，调度器会触发 preempt：

  • Recompute：丢弃部分序列的 KV，下次重新 prefill（最简单）。
  • Swap：把 KV 从 NPU 搬到 CPU 或 SSD（需 cpu_npu_block_allocator 支持）。
  • 策略由 maxPreemptCount 等参数与具体 policy 决定，避免抖动。

异步调度

对应 加速特性 → 异步调度：

  • 调度循环与 NPU 执行解耦，使数据准备 / 数据回收的 host 时间被 NPU 计算掩盖。
  • 实现层面通过额外的等待 / 唤醒线程与 maxQueueDelayMicroseconds 配合。

  4. 在 tests/dlt 与 tests/pythontest 补充对应单测。
  5. 在 开发与贡献 流程下提 PR。
