C++ 引擎内核

本章深入 src/engine/、 src/llm_manager/、src/executor/、 src/sequence/、src/config_manager/， 把 LLM Manager 内部各组件的协作关系讲清楚。

引擎核心：LLMEngine

核心类 LLMEngine（src/engine/llm_engine.cpp/h）是整个 LLM Manager 层的入口。它持有调度器、block manager、executor、buffered responser、 lora manager 等关键组件的所有权，并通过 mixin 注入扩展能力。

引擎主循环

  1. 请求接入：llm_manager_adapter 把 endpoint 传入的 LLMInferRequest 转成内部 InferRequestImpl。
  2. 构造 SequenceGroup：seq_group_builder_from_infer_req 把请求拆成 Sequence + SequenceGroup，挂入 LiveInferContext。
  3. 调度：scheduler.schedule() 选出本轮可执行的 batch， 并通过 block_manager 申请 KV blocks（命中 prefix cache 直接复用）。
  4. 组装执行包：construct_execute_request 把 batch 转成 worker 可消费的张量；遇到 LoRA 请求由 lora_manager 注入 adapter。
  5. 下发：executor 通过 gRPC / IPC 把执行包发给后端 worker。
  6. 回收输出：model_exec_output_handler 接收 token， 更新 SequenceGroup 状态，决定是否结束。
  7. 返回结果：buffered_responser 缓冲并按流式 / 整体两种模式 把 token 推回 endpoint。
  8. 资源释放：请求结束时 transfer_output_handler 协调 PD 分离场景下 KV cache 的传输；block_manager 回收所有 block。

Mixin 扩展机制

LLMEngine 采用 mixin 模式，避免基类爆炸。两个常用 mixin：

  • LayerwiseMixin：启用 layerwise 调度，支持 预填充 / 解码混合的细粒度执行编排，与 LayerwiseFCFS 调度策略配合。
  • LoraOpsMixin：把 LoRA 的 ops 注入到引擎执行路径， 把 base 权重的 forward 与 LoRA delta 的 forward 进行融合。

LLM Manager API

路径 src/llm_manager/，文件作用：

  • llm_manager.cpp：对外 C++ 接口实现。
  • llm_manager_adapter.cpp/h：把 LLMInferRequest 适配 成 InferRequestImpl，承担参数标准化。
  • infer_request_impl.cpp：内部请求实体，含 prompt / params / metadata / future。
  • llm_infer_request.cpp：对外暴露给用户的请求 DTO。
  • llm_infer_response.cpp：对外响应 DTO，含 token / finish_reason / usage。
  • infer_tensor.cpp：通用张量包装，跨 Python / C++ 共享。
  • python_api/：基于 pybind11 封装的 Python 入口。

新工程建议用更现代的 src/llm_manager_v2/，它提供更清晰的 接口分层（请求注册、状态查询、批量调度的解耦）。

Executor 与通信

路径 src/executor/。Executor 抽象「下发 batch 给 worker，等待 worker 返回结果」的语义，下面有两种实现：

  • GrpcCommunicator：跨进程 / 跨节点 gRPC 通信， 使用 proto/model_execute_data.proto 定义消息结构。
  • IpcCommunicator：同主机的高性能 IPC 通道， 典型基于共享内存（src/utils/ 中有共享内存工具）。

选择策略：单机多卡用 IPC，多机多卡用 gRPC。

Sequence 模块

路径 src/sequence/，建模请求生命周期：

  • Sequence：单个推理序列（一次 prompt → 多次 token）， 持有当前 token list、KV block 表、状态机（waiting / running / paused / finished）。
  • SequenceGroup：一批共享 prompt 的 Sequence（n>1 采样 / beam search），便于在调度上整体调度。
  • LiveInferContext：当前活跃请求的全局上下文， scheduler / block_manager 共享视图。
  • SchedulingBudget：本轮调度的预算 — 最多多少 token、 多少请求、显存余量；调度器用它控制 batch 大小。

Config Manager

路径 src/config_manager/。除了静态加载，还支持 运行时动态修改：

  • config_dynamic_handler.cpp：监听管理面 POST 请求，更新可热改的字段（如调度参数、日志级别）。
  • config_interaction.cpp/h：管理面与业务面共享的 交互层，用于 GET /v1/config / POST /v1/role/${role} 等接口。
  • param_checker.cpp：所有字段的范围 / 互斥校验， 失败立即返回明确错误。
  • ranktable_config.cpp：解析 ranktable JSON， 构建多机通信组拓扑。

LoRA Manager

对应 src/engine/lora_manager.cpp/h + Python 端 mindie_llm/runtime/lora/。功能：

  • 启动期注册基础权重；运行期支持 动态加载 / 卸载 LoRA adapter。
  • 每个请求可携带 lora_id，调度时 LoraManager 自动选择对应 adapter。
  • 多 LoRA 同 batch 共存通过 LoraOpsMixin 与 modeling 的融合 op 协作实现。

基础工具：src/utils/

包含日志、共享内存、加密、id 生成、字符串、时间等无业务依赖的工具。 其中：

  • 共享内存：用于主进程 ↔ worker 高速数据交换；切换用户后需 rm /dev/shm/* 清理（详见 FAQ）。
  • 加密：基于 OpenSSL 包装，配合 HTTPS 与 TLS 节点间通信使用。
  • id 生成：UUID / 雪花式 id，保证请求级别幂等。

Protocol Buffers

proto/model_execute_data.proto 定义主进程 → worker 的执行包 结构，主要字段包括：

  • request_ids、token_ids、kv_block_indices
  • 采样参数（temperature、top_k、top_p、repetition_penalty、stop tokens）
  • LoRA 配置 / 量化标记

对应 CMake 在 proto/CMakeLists.txt 中编译并发布给 server / executor 共用。

扩展指引

如果你要为 MindIE-LLM 新增一类调度策略 / KV 管理策略，建议从这些点切入：

  • 新调度策略 → 实现 scheduler/policy/policy.h 接口 → 在 policy_factory.cpp 中注册。
  • 新 KV 分配器 → 继承 device_aware_block_allocator.h → 在 self_attn_block_manager.cpp 中条件构造。
  • 新 worker 通信方式 → 实现 communicator.h 接口 → 在 executor.cpp 中按配置选择。
  • 新 endpoint 协议 → 在 endpoint/ 下添加 wrapper → 在 endpoint.cpp 注册路由。
