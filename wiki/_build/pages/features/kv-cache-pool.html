--- title: KV Cache 池化 ---

KV Cache 池化

把 NPU 显存之外的 DRAM（甚至 SSD）也纳入 prefix cache 池子， 突破单卡显存的容量限制，把命中率推到极致。

为什么需要二级缓存

NPU 显存就那么多 — 一旦填满，LRU Evictor 就要驱逐冷的前缀块；下次同样的前缀来了又得重新算。

KV Cache 池化把驱逐目标从「直接释放」改为「swap 到 DRAM」，下次命中时再 swap 回 NPU。容量从 GB 量级跳到 TB 量级。

   层级    介质         容量      访问开销     是否参与命中
   ────────────────────────────────────────────────────────
   L1     NPU HBM     ~ 100 GB   ns 级       立刻命中
   L2     CPU DRAM    ~ TB       μs 级       命中后 swap-in
   L3     SSD（可选）  ~ 数十 TB   ms 级       命中后两级 swap

在 MindIE-LLM 中的实现

由 CpuNpuBlockAllocator 实现两级管理：

  • 用同一个 BlockObjPool 服务 NPU + CPU 两侧；
  • blockId 落在统一空间：< beginCpuBlockId_ 是 NPU、否则 CPU；
  • 调度器在装 batch 时若发现命中的 prefix block 在 CPU，会一并下发 blocksToSwapIn_ 列表，由 worker 端做异步 NPU↔CPU 拷贝。

底层走 HCCL 单边通信池化后端，每条链路约 4 MB 显存，最大 512 条。多机场景下需相应下调 显存因子（默认 0.92，每下调 0.01 释放约 600 MB）。

配置

必须先开 Prefix Cache，再加上池化后端：

"BackendConfig": {
  "kvPoolConfig": {
    "backend":    "kv_pool_backend_name",
    "configPath": "/path/to/your/config/file",
    "asyncWrite": false        // true: 异步写，提高写入吞吐
  },
  "ModelDeployConfig": {
    "ModelConfig": [{
      "modelName": "dsr1",
      "plugin_params": "{\"plugin_type\":\"prefix_cache\"}",
      "models": {
        "deepseekv2": {
          "enable_mlapo_prefetch": true,
          "kv_cache_options": { "enable_nz": true }
        }
      }
    }]
  }
}

启动前先拉起池化后端的 Master Service（参考 mempool.md）。

收益

  • 多轮对话场景，命中率从 ~30% 提升到 70%+ 不罕见。
  • TTFT 在长 prefix 命中下降低 60–90%。
  • 注意：CPU↔NPU 带宽是关键瓶颈。带宽不够时收益会打折。

已知限制

  • Atlas 800I A2、Atlas 300I Duo 支持。
  • 其它限制与 Prefix Cache 一致。
  • 当前仅支持 DRAM 池化（与 Prefix Cache 叠加成两级缓存）。
  • 必须同时开 Prefix Cache。
  • 额外占片上内存：每条 HCCL 链路 4 MB，最多 512 条。
  • 构建池子建议总卡数 ≤ 512，避免 HCCL 频繁断链 / 重连。

调优建议

  • 会扩容场景：按最大显存因子下调 0.04 预留 HCCL 空间，避免动态加节点时 OOM。
  • 不会扩容：按公式 (总卡数 - 1) × 4 MB 计算 HCCL 占用，按需下调显存因子。
  • 显存因子下调一档 → 上下文长度需相应缩短，权衡。
