--- title: SplitFuse / Chunked Prefill ---

SplitFuse — 长 prompt 切块 + 与 decode 共 step 执行

把长 prompt 的 prefill 切成若干 chunk、与短请求的 decode 同 step 执行。让 batch 内每轮 forward 计算量更平均，时延更稳定，吞吐更高。

问题：长尾请求阻塞短请求

朴素的 prefill-first 调度：来了一个 16k 的 prompt，整个 batch 必须等它的 prefill 完成。 如果同时有 100 个短请求等待 decode，它们要被「卡」很久。

SplitFuse 的解

   每一轮 step：
     · 选一些 decode 请求，每个贡献 1 token；
     · 选一些 prefill 请求，每个贡献 chunkTokens 个 token；
     · 总 token 数控制在 maxPrefillTokens 以内；
     · 长 prefill 跨多 step 累计完成。

   step 0 :  [P1.chunk0=1024] [D2=1] [D3=1] [D4=1]
   step 1 :  [P1.chunk1=1024] [D2=1] [D3=1] [D4=1] ...
   ...
   step 7 :  [P1.chunk7=1024] [D2=1] [D3=1] [D4=1]   ← P1 完成 prefill
   step 8 :  [P1=1] [D2=1] [D3=1] [D4=1]              ← P1 进入 decode

价值

  • 响应速度：长 prompt 不再阻塞短请求 decode。
  • 计算效率：每 step 计算量近似相等，硬件利用率高。
  • 时延稳定：消除 batch 内长 prefill 引起的尖刺。

在调度器中的实现

详见 scheduler → ScheduleChunkedPrefill。 关键在两处：

  • SchedulingBudget：维护 partialPrefillOccupiedBudgetPerSlot_ 列表，根据当前并发 partial prefill 数量决定每位 slot 占多少 token 配额。
  • Statistics4PartialPrefill：在每轮 schedule 之前统计 long-prefill 数量， 决定能否再纳入新请求。

配置

"ModelConfig": [{
  "modelName":       "llama3-70b",
  "modelWeightPath": "/home/models/llama3-70b/",
  "worldSize":       8,
  "plugin_params":   "{\"plugin_type\":\"splitfuse\"}"
}],
"ScheduleConfig": {
  "templateType":              "Mix",
  "maxPrefillBatchSize":       40,
  "maxPrefillTokens":          65536,
  "maxBatchSize":              256,
  "prefillChunkSize":          1024,    // 固定切分长度（不配置则动态切）
  "maxNumPartialPrefills":     64,      // batch 内并行 partial prefill 上限
  "longPrefillTokenThreshold": 1024,    // ≥ 此值认为是「长 prefill」
  "maxLongPartialPrefills":    8        // 同时进行的长 prefill 上限
}

调优思路（按 AISBench 测试结果）

  • TTFT、TPOT 都达标 → 提高 RequestRate 测吞吐。
  • TTFT 超阈、TPOT 达标 → 降低 RequestRate（此时已超系统能力）。
  • TTFT 达标、TPOT P90 不达标 → 降低 prefillChunkSize， 减小切分（可能略损吞吐）。
  • 输入分布不一 → SplitFuse 优势更明显。

已知限制

  • Atlas 800I A2 / A3 支持。
  • LLaMA3.1-70B 浮点、Qwen2 / 2.5 / 3 系列支持。
  • 仅支持 W8A8 量化；其它量化暂不支持。
  • 不能与 Multi-LoRA、Function Call、 并行解码、MTP、长序列特性同时使用。
  • 支持 n、best_of、use_beam_search 后处理参数。

收益（典型）

  • 输入长短不一的混合负载，吞吐 +20–40%。
  • 长 prompt 比例越高，收益越明显。
