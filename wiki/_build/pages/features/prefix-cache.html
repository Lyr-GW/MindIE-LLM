--- title: Prefix Cache ---

Prefix Cache（前缀缓存）

把上一轮 session 的 KV Cache 通过前缀哈希保留下来， 新请求若有相同前缀直接命中复用，跳过整段 prefill。是多轮对话 / few-shot 场景的杀手级特性。

两个动机

  • 显存压力：长上下文 KV 体积大，希望多个公共前缀的请求共享同一份 KV。
  • 跨 session 复用：朴素 KV Cache 只对当前 session 有效；session 结束后被释放。

怎么命中

详细机制见 block-manager → PrefixCacheBlockAllocator。 简化版：

每个 block 计算 prefixHash = HashCombine(parent_hash, tokens, extra_hash)
分配新 block 时先 cachedBlocks_.find(hash)
命中 → 复用并 +1 引用计数
未命中 → 申请新 block，写入 cachedBlocks_[hash] = block_id

三个细节决定可命中性：

  • 必须整 block 填满才有 hash。
  • 父 hash 缺失则当前 hash 无效（必须从 block 0 起复用）。
  • extraHash 把 LoRA / 量化模式吃进去，避免错配。

如何开启

"ModelConfig": [{
  "modelName": "DeepSeek-R1_w8a8",
  "plugin_params": "{\"plugin_type\":\"prefix_cache\"}",
  "modelWeightPath": "/data/weights/DeepSeek-R1_w8a8",
  "worldSize": 8,
  "models": {
    "deepseekv2": {
      "kv_cache_options": { "enable_nz": true }   // DeepSeek 必开
    }
  }
}]

多个插件可叠加，用英文逗号分隔：

"plugin_params": "{\"plugin_type\":\"mtp,prefix_cache\",\"num_speculative_tokens\":1}"

命中率指标

HitRateCalculator 维护滑动窗口的命中率， 通过 /metrics 暴露。命中率 ≥ 30% 时收益明显；持续 < 5% 时建议关闭以节省哈希开销。

什么时候收益最大

  • 多轮对话：每次请求都包含历史对话，前缀复用率极高。
  • Few-shot prompting：固定的 system prompt + 示例占比高。
  • API 编排：固定 schema 模板。

实战示例

第一次请求：

curl https://127.0.0.1:1025/generate -X POST \
  -d '{"inputs": "Question: ...一段 1k token 的题目和选项...\nAnswer:",
       "parameters": {"max_new_tokens": 512}}'

第二次请求（保持前缀，追加新内容）：

curl https://127.0.0.1:1025/generate -X POST \
  -d '{"inputs": "Question: ...同上 1k token...\nAnswer: 上一轮答案\n\
                   Question: 新一轮问题\nAnswer:",
       "parameters": {"max_new_tokens": 512}}'
# 第二次 prefill 时，前 1k token 直接命中 KV Cache，TTFT 显著降低

注意：复用按 block 对齐 — 比如第一轮 prompt 164 token、blockSize=128 时， 实际复用前 128 token；剩 36 token 仍需 prefill。

已知限制

  • Atlas 800I A2 / A3、Atlas 300I Duo 支持。
  • Qwen2 / 2.5 / 3、DeepSeek-R1 / V3 / V3.1 支持。
  • 支持 W4A8 / W8A8 / PDMIX / 稀疏量化；其它量化暂不支持。
  • 不能与 Multi-LoRA 同开。
  • PD 分离场景：仅 P 节点开启。
  • 不支持 prefix cache + CP + SP + function call(multiturn) 叠加。
  • 命中率低时不要开。
