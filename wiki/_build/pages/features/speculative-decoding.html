--- title: 投机解码 / Lookahead ---

投机解码（Speculative Decoding）— 用算存比把 decode 吞吐拉起来

「用一次 forward 同时生成 / 验证 K 个 token」是 LLM 推理领域近三年 最重要的吞吐优化思想。本章从 算存比（Arithmetic Intensity） 出发，把投机解码的原理、 数学、业界全景与 MindIE-LLM 的实现讲透；并给出工程调优方法论。

📚 阅读路线

1–3 节：为什么 decode 是访存瓶颈，投机解码如何「白嫖」算力 —— 即使是新人也能看懂。
4–5 节：业界主要算法的 1 张图 + 1 段公式综述。
6–7 节：MindIE-LLM 内置 memory_decoding / la 的工程实现细节。
8–9 节：调优 + 失败模式 + 未来。

1. Decode 阶段的「算存比悖论」

Prefill vs Decode：完全不同的硬件画像

                       Prefill                 Decode
   每次 forward 算多少 :  L 个 token            1 个 token
   权重读取             :  整个模型 1 遍         整个模型 1 遍
   计算 / 访存比       :  ~ L 次 / 字节         ~ 1 次 / 字节
   硬件画像             :  Compute-bound        Memory-bound
   GPU/NPU 利用率      :  > 70%                10–30%

看个 70B 稠密模型的真实数字（fp16，单卡）：

  • 权重总量：~140 GB；
  • HBM 带宽：~1.5 TB/s；
  • 读完整组权重：140 / 1500 ≈ 90 ms — 这就是 decode 单步的访存下限；
  • 算力：~300 TFLOPS（fp16）；
  • 实际单步算力需求：每个 token 约 2 × 70B FLOPs = 140 GFLOPs；
  • 占总算力比：140 GFLOPs / (300 TFLOPS × 0.09 s) ≈ 0.5%。

结论：Decode 阶段 NPU 算力 99% 在空转，瓶颈是带宽。

「算存比」的数学定义

Arithmetic Intensity (AI)
  ≜ 算子的 FLOPs / 算子访问的字节数
  单位 : FLOPs / Byte

设备的「拐点 AI」
  ≜ 设备峰值算力 (FLOPs/s) / HBM 带宽 (Byte/s)
  对昇腾、A100、H100 都是 100~400 区间

Roofline 模型：

   性能 (FLOPs/s)
        │      ┌────────── 受算力限     (compute-bound)
        │     ╱
        │    ╱
        │   ╱
        │  ╱  ← 受带宽限 (memory-bound)
        │ ╱     性能 = AI × 带宽
        ╰────────────────────────────→  AI (FLOPs/Byte)
        ↑              ↑
       低 AI         拐点 AI
     decode 在这       prefill 在这

Decode 单 token 的 AI ≈ 1，远低于 设备拐点的 100–400；落在斜率部分，性能由 带宽线性决定。这意味着：每 byte 数据吐出的 token 越多，吞吐越高。

为什么单纯增大 batch 不够？

大 batch 是直观解法 — 同一份权重服务 N 个请求，AI 提升 N 倍。但实践中：

  • 显存上限：KV Cache 与 batch 线性增长，64 路并发后显存往往打满。
  • SLO 限制：batch 越大每步越慢，TPOT 上升，长尾用户体验下降。
  • 请求到达不均：低 QPS 时空 batch 比比皆是。

所以即便已经「调大 batch」，仍要找另一种增大 AI 的方式 — 这就是投机解码的切入点。

2. 投机解码的核心 idea

把传统 decode：

   step t   : 读权重 一次 → 算 1 token →  out_t
   step t+1 : 读权重 一次 → 算 1 token →  out_{t+1}
   step t+K : 读权重 一次 → 算 1 token →  out_{t+K}
                ↑↑
        每步只产 1 token，AI ≈ 1

改成：

   step S   : 廉价 draft 模型 / 算法 → 给出 γ 个候选 token
   step V   : 主模型读权重 一次 → 一并验证 γ 个 token →  通过 k 个 (k ≤ γ)
                ↑↑
        权重只读一次，但产 1+k 个 token，AI ≈ 1+k

关键观察：主模型一次 forward 的访存与 batch=γ 是一样的（都是把权重整套读一遍）， 但是每个 token 的输出都享受到了同一次权重读取 — AI 直接放大 1+k 倍。 又因为 decode 阶段算力本来就是空转的，加一点 verify 计算也几乎不增加单步耗时。

这就是 「用算力换访存，反过来用访存喂算力」的本质。

3. 期望加速：数学公式

设：

  • γ：每轮 draft 提交的候选 token 数（speculation length）；
  • α：单 token 接受率（draft 与主模型预测一致的概率）；
  • c：draft 模型 vs 主模型 forward 的成本比率（< 1）；
  • τ：主模型一次 forward 的耗时；

朴素 decode 每 token 耗时为 τ。投机解码每个 verification 周期：

T_period   = γ·c·τ + τ                       // draft + 1 次 verify
E[tokens]  = (1 − α^(γ+1)) / (1 − α)         // 这一轮预期吐出 token 数
                                              // 简化记号：α=0 时降为 1，α=1 时趋于 γ+1

加速比     = E[tokens] / (γ·c + 1)
            ≈ (1 − α^(γ+1)) / [(1 − α)(γ·c + 1)]

三个直觉：

  • α 越高，加速越大。draft 越像主模型越好。
  • γ 不能太大。γ 大了 draft 成本占比也大，且 α^(γ+1) 接近 0；存在最优 γ*。
  • c 越小越好。这就是 「draft 模型要尽可能廉价」 的来源。

典型场景下（α=0.7, c=0.05, γ=4），加速比 ≈ 2.5–3 倍 — 这与 Google 原始论文（α=0.6, ~2x）、 EAGLE-2（α=0.85, ~3x）的实测一致。

4. 业界投机解码全景图

所有方案都在回答两个问题：「draft 哪来？」「verify 怎么做？」

① Draft 来源

来源典型方案特点
独立小模型 Speculative Decoding (Leviathan, Google '23) 用同家族小一档模型（7B vs 70B）。最直接、最经典；要训练 + 部署 draft。
模型自身的多输出头 Medusa, Medusa-2 给主模型加 N 个并行输出头，每个头预测「下下个」「下下下个」。无需 draft 模型；需要轻量微调。
模型自身的特征自回归 EAGLE, EAGLE-2, EAGLE-3 把主模型的 hidden state 作为 draft 输入，再一个轻量自回归头预测下一 hidden 与 token。比 Medusa 更准。
主模型自迭代 Lookahead Decoding (Fu et al., UCSD '24) 用 Jacobi 迭代从主模型自身的 N-gram 缓存生成候选；不需要训练，但接受率较低。
检索 / 缓存 REST, PLD, Memory Decoding 从 prompt / 历史输出 / 知识库里检索相似 token 串作为候选。代码、长文档场景接受率极高。
自跳层 Self-Speculative Decoding 主模型「跳一些层」做 draft，再用全层 verify。零额外参数。
训练时多 token 监督 MTP（DeepSeek-V3） 训练阶段就让模型学会预测多个未来 token，自带 MTP head。接受率最高、最稳定。

② Verify 结构

结构说明代表
Sequence (γ-token) 把 γ 个候选当作一段拼到 prompt 后，主模型一次 forward 输出 γ+1 个 logits， 逐个比对至首个不一致位置。 原始 Speculative Decoding
Tree (token 树) 同一次 forward 验证多条候选路径（共享前缀的 trie）；接受率 ↑。 SpecInfer / Medusa-2 / EAGLE-2
Tree + 排序剪枝 验证前对树节点用 draft 概率打分，仅保留 top-K 子树进 verify。 EAGLE-2 / EAGLE-3

③ 接受规则

// 原始论文（无偏精确）：rejection sampling
if  rand() < min(1, p_main(t) / p_draft(t)):
    accept t
else:
    reject t,  resample from   max(0, p_main(t) − p_draft(t))

// 工程优化（贪婪 / 低温场景常用）：top-1 比对
if  argmax p_main == draft_token:
    accept
else:
    reject (replace with main's argmax, 后续候选丢弃)

原始规则保证分布无偏（输出与主模型完全一致）；top-1 比对在 temperature ≤ 0.7 / 贪婪场景 实践中差异极小，但实现极简单，是大部分工程实现的默认。

5. MindIE-LLM 提供哪些

本仓库内置 3 套投机解码方案：

  1. memory_decoding — 检索式（前缀树），适合代码 / 长文档；
  2. la (Lookahead Decoding) — 自迭代式（Jacobi），适合通用对话；
  3. MTP — 训练时多 token 监督（仅 DeepSeek-V3 / R1 系列）。

对应 mindie_llm/text_generator/plugins/：

plugins/
├── la/                 # Lookahead 实现：Jacobi 迭代 + N-gram 池
├── memory_decoding/    # 前缀树（trie）缓存
├── mtp/                # MTP head 调用 + 多 token 校验
└── plugin_manager.py   # 三者共享的调度钩子

memory_decoding 详解

核心数据结构：每模型实例一棵全局 Trie 树，节点存 token id，每条边权重为出现频次。 新输入 / 输出 token 都被插入到 trie。

// 每步 decode 前
prefix_window = last_K_tokens_of_current_seq      // K = 4 或 8
candidates    = trie.match_longest_branch(prefix_window, max_len = decoding_length)
candidates    = candidates[: γ]                    // 截断到 γ
// 主模型一次 forward 验证 candidates

当 dynamic_algo=true，根据上一轮的实际接受 token 数动态调整下一轮 γ：

if  acc_rate < 0.3 :  γ ← max(1, γ − 1)        // 命中率太差，缩短候选
elif acc_rate > 0.7 :  γ ← min(decoding_length, γ + 1)  // 命中率好，加长 ROI

命中率：

  • 代码生成（自身 token 重复率高）：α ≈ 0.7–0.85；
  • 检索 / 翻译（输入也在 trie 里）：α ≈ 0.6–0.8；
  • 开放对话：α ≈ 0.3–0.5（不适合，建议改用 la 或 MTP）。

la (Lookahead Decoding) 详解

Lookahead 是 UCSD 团队 2024 年提出的方法，不需要任何 draft 模型 / head。 它把单步 decode 改造成 Jacobi 迭代：

原始 (Auto-Regressive) :
  y_1 = f(x, [y_0])
  y_2 = f(x, [y_0, y_1])
  ...

Jacobi （并行猜并行修正）:
  initialize  ŷ = [random / repeated tokens]    长度 W (window)
  while not converged:
      ŷ' = f(x, ŷ)      // 一次 forward 同时算 W 个位置
      若 ŷ' 与 ŷ 在前 k 位一致 → accept k 个 token
      否则 ŷ ← ŷ' 继续迭代

Lookahead 在 Jacobi 之上叠了两个增强：

  • N-gram pool：每次迭代收集出现的 N-gram，存到一个池里。下一次迭代用池里的 N-gram 作为「候选种子」，加速收敛。
  • Verification branch：每步同时验证池中的多个候选（树状），多分支并行 verify。

三个超参数：

level (N) ∈ [3, 16]   N-gram 长度（越长越准但越难命中）
window (W) ∈ [1, 16]  每步并行猜的位置数
guess_set_size (G)    每步 verify 的候选分支数

论文经验：N=4, W=5, G=5 是大多数任务的甜点。speculationGamma ≥ (N−1)·(W+G) 是 引擎侧的预算配置（保证 KV slot 够用）。

MTP 详解（链接）

MTP 详见 MTP 详解页。它是训练阶段就引入的多 token 预测， 所以接受率比 la / memory_decoding 高得多（α ≈ 0.85+）。代价是模型必须自带 MTP head（DeepSeek-V3 系 原生支持）。

7. 什么场景用哪个？

场景特征推荐原因
代码 / SQL / 模板填充 memory_decoding 历史 N-gram 高度重复，trie 命中率最高
长文档摘要 / 检索式问答 memory_decoding prompt 的 token 在输出中频繁出现
开放对话 / 创作 la 无明显重复，但 Jacobi 自迭代仍可救出 1.5–2x
DeepSeek-V3 / R1 上的所有场景 mtp 原生 MTP head 接受率最高，吞吐 +30–60%
低温度 / 贪婪解码 三者皆收益放大 top-1 比对接受率上升

   是 DeepSeek-V3/R1 ?
        │
        ├─ Yes →  MTP
        └─ No  →  代码 / 长文档 / 检索  →  memory_decoding
                  其它（对话 / 创作）   →  la

8. 工程调优方法论

第 1 步：测出当前接受率 α

开启投机解码后，从日志或 /metrics 中读 speculative_accept_rate。 也可以手动测：跑同一 prompt 100 次，统计 verify 通过数 / 总 verify 数。

第 2 步：根据 α 选 γ

对加速比公式求 γ 偏导可得最优解，工程上记忆三档即可：

α ≈ 0.5 → γ* ≈ 2~3
α ≈ 0.7 → γ* ≈ 4~6
α ≈ 0.85+ → γ* ≈ 7~10

γ 太大的副作用：

  • 每轮多吃 KV slot（maxBatchSize 受限）；
  • 调度更不稳定（每轮实际产 token 数方差大）；
  • α^(γ+1) 急速衰减时收益变负。

第 3 步：vs 不开测对比

不要相信论文宣称的 X 倍 — 在你的 batch / SLO / 输入分布下重测：

# 比较
ais_bench --models vllm_api_stream_chat --datasets ... --mode perf
# 关注三个指标：
#  Output Token Throughput  ← 是否真的提升
#  TPOT (P99)              ← 是否引入抖动
#  TTFT                    ← 投机解码常常让 prefill 期间多算 trie，TTFT 略升

第 4 步：监控生产

  • 实时跟踪 α 滑动窗口；α 持续下降可能是分布漂移（业务变化），考虑切换算法或关闭。
  • 监控 KV 命中率：投机解码会消耗更多 KV slot，可能让 OOM 风险上升。

9. 常见失败模式 / 避坑

  • γ 调太大、命中率反降。trie 太深 / Jacobi 长链都会让接受率断崖。 表现：开了反而更慢。解：先用 dynamic_algo=true 让引擎自适应。
  • 高温度 + 投机解码。分布扁平后 top-1 比对的接受率近似 α ≈ 1/V_eff（V_eff 是有效词表大小），收益消失。解：开 temperature ≤ 0.7 或换无偏 rejection sampling 路径。
  • KV slot 抢占。投机解码每个序列每轮多占 γ 个 slot；调度器看到同样 maxBatchSize 但实际占用 ×(γ+1)。解：相应调小 maxBatchSize 或调大显存因子。
  • 流式接口表现奇怪。一次吐 1+k 个 token 的「跳跃」会让前端动画 不平滑。解：前端做 token 平滑展示（每 30 ms 吐一个）。
  • MTP / la 与 SplitFuse 等冲突。详见 兼容矩阵。 这些组合需要对调度器做较大改造，目前 MindIE-LLM 选择了「互斥」路线。

10. 前沿与未来

三个值得关注的方向：

  1. EAGLE-3 + Tree Verify（2024–2025）：用主模型 hidden state 自回归生成 draft，配合 token 树 verify，业界报告 SOTA 加速比 3–5×。MindIE-LLM 短期内可能引入类似形态。
  2. Tandem / Heterogeneous：用不同位宽的同模型做 draft（如 W4A8 当 draft、 W8A8 当 main），训练 0 改动 + 部署同权重。
  3. Continuous Speculative：让投机解码与 Continuous Batching 深度融合， 每轮 batch 中允许「不同序列采用不同 γ」 — 这是当前调度器最棘手但收益最大的优化点。

已知限制（合并自前一版）

  • 暂不支持开启 HealthCheck。
  • la 与 memory_decoding 不可同时使能。
