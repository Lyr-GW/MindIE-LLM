KV Cache 与 Block Manager

这一章把 src/block_manager/ 整个目录拆开看： 为什么大模型推理要做 KV 分块、MindIE-LLM 的 Block 对象长什么样、 多个分配器是怎么协作的、引用计数 / LRU / CoW / 前缀哈希 / CPU↔NPU 池化怎么实现， 最后给出调优与扩展指引。每节都附关键源码片段。

📚 阅读路线

第 1–3 节是「为什么」与「概念」，新人按顺序读即可；4–7 节是「实现」与 源码摘录；8–9 节是「调优」与「扩展」。读完你应该能在源码里精准定位任何 KV 相关 问题。

1. 为什么需要 Block Manager

大模型推理时每生成 1 个 token，就要把这个 token 的 K / V 张量缓存起来供后续使用， 这就是 KV Cache。朴素实现给每个序列预留「最大长度 × 头数 × 维度」 的连续显存，会带来三个严重问题：

  1. 显存浪费：实际请求长度往往远小于最大长度，未用空间被锁住。
  2. 无法共享：相同 prompt 的多请求重复算 KV，重复占空间。
  3. 无法弹性：突发长请求需要中断或拒绝。

PagedAttention 的解法是：把 KV 切成固定大小的 Block（如 16 token）， 每个序列持一张「page table」（block 索引数组）。MindIE-LLM 在此之上叠加了 Prefix 共享、CoW 分裂、LRU 驱逐、CPU/NPU 异构池化。

2. Block 对象：最小存储单元

看 src/block_manager/block_obj.h 中 BlockObj 的接口（精简，去除注释）：

// 摘自 src/block_manager/block_obj.h
class BlockObj {
public:
    virtual void          AppendTokenIds(const std::vector<TokenId>& tokenIds) = 0;
    virtual BlockId       GetBlockId() const = 0;
    virtual size_t        GetRankIdx() const = 0;          // 属于哪一卡（rank）
    virtual const std::vector<TokenId>& GetTokenIds() const = 0;
    virtual size_t        GetNumTokensTotal() const = 0;   // 含前驱链
    virtual bool          IsFull() const = 0;
    virtual std::shared_ptr<BlockObj>& GetPrevBlock() = 0; // 形成链表
    virtual bool          IsComputed() const = 0;          // KV 是否真已写入
    virtual float         LastAccessed() const = 0;        // LRU 用
    virtual HashValue     GetHashValue() = 0;              // PrefixCache 用
    virtual HashValue     PrefixHash() = 0;                // 含前驱
    virtual HashValue     ExtraHash() = 0;                 // LoRA 等额外因子
    virtual void InitBlockObj(...);
    ...
};

关键认知：

  • 每个 Block 持固定容量的 token id 数组（容量 = blockSize）。
  • Block 通过 GetPrevBlock() 形成链表，反映「这块 KV 是基于哪个前缀算出来的」。
  • PrefixHash() 把整条前缀链一并哈希，让多请求复用前缀。
  • ExtraHash() 给 LoRA、量化模式等额外维度留口子，避免不同 LoRA 共享同一段 KV。

顶层管理器 SelfAttnBlockManager（以及 layerwise 版本 LwdSelfAttnBlockManager）只关心「分配 / 释放 / 是否还能塞下」，具体怎么 分配交给可插拔的 DeviceAwareBlockAllocator。

4. 分配器矩阵

4.1 HashlessBlockAllocator — 最朴素的 free list

对应 src/block_manager/hashless_block_allocator.cpp。 它不做任何前缀复用，只维护两个集合：「全部 block 索引」与「空闲 block 索引」。 申请就 pop_front，释放就 push_back。优势：实现简单 + O(1)。

4.2 PrefixCacheBlockAllocator — 前缀复用

这是 MindIE-LLM 默认开启的分配器（位于 prefix_cache_block_allocator.cpp）。核心思路是把 prefixHash → blockId 存成一张 cachedBlocks_ 表； 申请 immutable 块时先查表：

// 精简自 PrefixCacheBlockAllocator::AllocateImmutableBlock
auto block = blockObjPool_->AcquireObj();
block->InitBlockObj(prevBlock, tokenIds, sharedAttr, INVALID_BLOCKID, extraHash);

HashValue key = block->PrefixHash();         // ① 计算前缀哈希
auto it = cachedBlocks_.find(key);

if (it != cachedBlocks_.end()) {            // ② 命中：复用旧 block
    block->SetBlockId(it->second);
    hitRateCalculator_->Record(true);
    IncrRefCountCacheBlock(block);
    return block;
}

// ③ 未命中：申请新 mutable，写入 cachedBlocks_
hitRateCalculator_->Record(false);
...

命中后该 block 引用计数 +1，多个请求共享同一个 block，直接跳过 prefill 计算。

4.2.1 PrefixHash 是怎么算的

看 prefix_cache_block.cpp：

// 精简自 PrefixCachingBlockObj::PrefixHash
if (cachedPrefixHash_ != INVALID_HASH_VALUE) return cachedPrefixHash_;
if (!IsReadyToCalcPrefixHash()) return INVALID_HASH_VALUE;   // 必须填满 + 末位非 placeholder

auto preBlock = GetPrevBlock();
if (preBlock && preBlock->PrefixHash() == INVALID_HASH_VALUE) return INVALID_HASH_VALUE;

HashValue seed = 0;
if (preBlock) HashCombine(seed, preBlock->PrefixHash());     // 拼接父 hash
for (TokenId t : GetTokenIds())  HashCombine(seed, t);       // 当前 token 序列
HashCombine(seed, extraHash_);                                // LoRA / 量化区分

cachedPrefixHash_ = seed;
return seed;

三个细节决定可命中性：

  • 必须填满整 block 才有 hash — 半填的尾块永远不能命中。
  • 父 hash 缺失则当前 hash 也算不出 — 复用必须从 block 0 顺次。
  • extraHash 把 LoRA id / 量化模式吃进去，避免错配。

4.3 CpuNpuBlockAllocator — 异构两级池

当 NPU 显存不够，把冷 KV 暂存到 CPU DRAM。看 cpu_npu_block_allocator.cpp：

// 精简自 CpuNpuBlockAllocator 构造
// CPU allocators 数 = hostSize_，对应主机视角的多份副本
for (size_t i = 0; i < hostSize_; ++i) {
    cpuAllocators_.emplace_back(make_shared<PrefixCacheBlockAllocator>(
        beginCpuBlockId_ + numCpuBlocks * i, numCpuBlocks, blockSize, blockObjPool));
}
// NPU allocators 数 = rankSize_，每张卡一份
for (size_t i = 0; i < rankSize; ++i) {
    npuAllocators_.emplace_back(make_shared<PrefixCacheBlockAllocator>(
        beginNpuBlockId, numNpuBlocks, blockSize, blockObjPool));
}

两侧共享同一个 BlockObjPool（块对象池），blockId 用一个连续 整数空间区分位置：

DeviceType CpuNpuBlockAllocator::GetDeviceTypeForBlockId(BlockId blockId) const {
    return (blockId < beginCpuBlockId_) ? DeviceType::NPU : DeviceType::CPU;
}

Swap（CPU↔NPU 搬运）通过维护 swapMapping_ 列表， 由调度器在 batch 装配时打包成 blocksToSwapIn / blocksToSwapOut 一并下发。

5. 引用计数：避免错释放

ref_counter.cpp 50 行就是全部：

// 精简自 RefCounter
RefCount RefCounter::Increase(BlockId id) { return ++refCounts_[id]; }
RefCount RefCounter::Decrease(BlockId id) { return --refCounts_[id]; }
RefCount RefCounter::GetRefCount(BlockId id) const { return refCounts_.at(id); }

规则：

  • 新 block：refCount = 1（创建者持有）。
  • 命中 prefix cache：refCount += 1（多一个序列共享）。
  • 序列结束：遍历 BlockTable，每块 refCount −= 1。
  • refCount 归 0 → 进入驱逐候选；归 0 且非 prefix-cached → 直接回收。

6. Copy-on-Write：共享 block 的安全分裂

当多个序列共享同一前缀 block，但其中一个要在该 block 内写入不同的 token（采样发散、beam search、并行采样），就需要 CoW。看 copy_on_write_tracker.cpp：

// 精简自 CopyOnWriteTracker
bool CopyOnWriteTracker::IsAppendable(BlockId blockId) const {
    RefCount refCount = refCounterSPtr_->GetRefCount(blockId);
    return refCount <= 1;          // 唯一持有 → 直接追加
}
void CopyOnWriteTracker::RecordCow(BlockId src, BlockId tgt) {
    copyOnWrites_.emplace_back(src, tgt);
}
auto pairs = cowTracker.ClearCows();   // 调度器读出来一并下发到 worker

当 IsAppendable=false：分配器会申请新 block、把旧 block 内容复制过去， 并通过 RecordCow(src, tgt) 留个迁移记录；调度器把这些 (src,tgt) 对 塞进 blocksToCopy_，下发到 worker 触发 NPU 上的内存复制。

7. LRU 驱逐

当 free list 空了，需要驱逐 refCount=0 的 block 让位。看 lru_evictor.cpp 的核心：

// 精简自 LRUEvictor
struct BlockMetaData { BlockId blockId; HashValue prefixHash;
                       size_t numHashedTokens; TimeStamp lastAccessedTime; };
// candidates_: BlockId → BlockMetaData （最新视图）
// priorityQueue_: 优先级队列，按 lastAccessedTime 升序

EvictionResult LRUEvictor::Evict() {
    while (!priorityQueue_.empty()) {
        auto data = priorityQueue_.top(); priorityQueue_.pop();
        auto it = candidates_.find(data.blockId);
        // 双重确认：堆里的时间戳与 candidates_ 里一致才真驱逐
        if (it != candidates_.end() && IsClose(it->second.lastAccessedTime, data.lastAccessedTime)) {
            HashValue prefixHash = it->second.prefixHash;
            candidates_.erase(it);
            return {prefixHash, data.blockId};
        }
    }
    throw std::runtime_error("No usable cache memory left");
}

这里有个工程细节：每次 Update(blockId, lastAccessedTime) 不会动堆 — 而是 简单地刷新 candidates_ 中的时间戳；驱逐时用双重时间戳一致性检查 跳过过期项。当堆膨胀到 candidates_.size() × LRU_EVICTOR_CLEANUP_THRESHOLD 时调用 Cleanup() 重建堆。这避免了每次 update 都做 O(log n) 的 decrease-key。

8. 命中率统计

每次 AllocateImmutableBlock 调用都会在 hitRateCalculator_->Record(true|false) 留一笔， HitRateCalculator 维护滑动窗口供 /metrics 读取。 命中率持续 < 5% 时建议关闭 prefix cache 节省哈希开销。

10. 一次完整生命周期

  1. 请求到来：调度器调用 blockManager->CanAllocate(seqGroup) 返回 OK / LATER / NEVER。
  2. 查 prefix cache：PrefixCacheBlockAllocator 计算 hash 逐 block 比对；命中 K 个则直接复用并 +1 引用。
  3. 申请新 block：剩余 N − K 个走 free list 或触发 LRUEvictor::Evict()。
  4. 建表：写入序列 BlockTable，发回调度器。
  5. token 增长：每次新 token AppendTokenIds；填满则申请下一块； 填满且非 placeholder 才计算 PrefixHash 加入 cachedBlocks_。
  6. 分裂场景：若该 block 被 fork，CoW Tracker 触发复制并改写表项。
  7. 序列结束：遍历 BlockTable 给每块 refCount −1；归 0 进入驱逐候选。
  8. 显存紧张：调度器请求驱逐若干块，LRUEvictor 给出受害者； 若启用 KV 池化，先 Swap 到 CPU 而非直接释放。

11. 排障常用思路

  • OOM → 减小 maxBatchSize / maxPrefillTokens；启用 KV Int8。
  • Prefix 命中率低 → 把请求模板里的变量前缀（时间戳、用户 id）后置。
  • Swap 抖动 → 检查 CPU 池容量、CPU↔NPU 带宽。
  • 引用泄漏 → 在 HitRateCalculator 与 BlockTracker 加日志， 通常发生在异常请求中断路径。
