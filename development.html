开发与贡献

如果你打算修改 MindIE-LLM、为它实现新特性、或者把自家模型适配进来， 本章给出代码规范、构建测试、PR 流程的完整指引。

开发环境

  1. 推荐方式：在仓库的 .devcontainer/ 里启动 VS Code Dev Container — 预装 CANN、ATB、g++、cmake、pre-commit。
  2. 本地手搭：参考 源码编译 章节， 装齐 CANN / ATB / Python 3.11 / g++ ≥ 9 / CMake ≥ 3.20。
  3. NPU 与硬件：开发环境最好带至少 1 张 NPU；纯算法 / 工具开发可以 无 NPU 但需要 mock 设备。

代码风格

C++ 规范

仓库根目录提供 .clang-format 与 style.cfg，pre-commit 会自动检查。 关键约定：

  • 命名
    • 类 / 结构体：PascalCase（如 LLMEngine）
    • 方法 / 局部变量：camelCase（如 scheduleNext()）
    • 常量 / 宏：SCREAMING_SNAKE_CASE（如 MAX_BATCH_SIZE）
    • 成员变量：m_ 或 _ 前缀（如 m_blockManager）
    • 枚举：enum class，强类型
  • 语言特性
    • 优先 auto / range-based for / 智能指针
    • 资源管理一律 RAII；不要 new/delete
    • 所有权用 unique_ptr，共享用 shared_ptr，弱引用 weak_ptr
    • 类型安全替代：std::optional / std::variant / std::any
    • 编译期能算的用 constexpr
    • 只读字符串用 std::string_view
    • 禁用 C 风格强转，改用 static_cast / dynamic_cast / reinterpret_cast；明确 const
  • 错误处理：边界使用异常（std::runtime_error、 std::invalid_argument），核心路径辅以错误码；统一通过日志库（spdlog 风格） 记录 ERROR / WARN。
  • 头文件：接口与实现分离；公共接口放 src/include/。
  • 性能：避免不必要堆分配；移动语义 std::move； 热路径用 <algorithm>。

Python 规范

  • 遵循 PEP8；缩进 4 空格；行宽 ≤ 120。
  • 类型注解必须有：参数 / 返回值。
  • 避免裸 except；用具体异常类型。
  • 日志用 mindie_llm.utils.logger，禁用 print。
  • 张量维度注释（# [B, S, H]）有助于审阅。

pre-commit 钩子

pip install pre-commit
pre-commit install
pre-commit run --all-files   # 第一次跑跑看

钩子覆盖：clang-format、isort、black、flake8、行尾空格、禁用 secret 等。 详见 .pre-commit-config.yaml 与 pre-commit/。

构建

详见 安装与编译。开发常用命令：

# 仅构建 src 增量（最快）
bash scripts/build_src.sh

# 编辑安装 Python 包（改 .py 立即生效）
pip install -e .

# 重启服务
mindie_llm_server

测试

C++ 测试

  • tests/dlt：数据 / 张量 / block_manager / scheduler 等模块的单测。 基于 GTest，构建后用 ctest 或直接执行二进制。
  • tests/fuzztest_llmmanager：针对 LLM Manager 的模糊测试， 随机化输入找崩溃 / 内存错误。

Python 测试

  • tests/pythontest：基于 pytest。
  • 跑全套： 
    pip install -r tests/requirements.txt
bash tests/run_all_tests.sh
  • 跑单个用例： 
    pytest tests/pythontest/path/to/test_xxx.py -k 'test_case' -s

扩展点

新增调度策略

  1. 在 src/scheduler/policy/ 新建 my_policy.cpp/h， 继承 IPolicy。
  2. 在 policy_factory.cpp 加分支：根据 ScheduleConfig.templateType="MyPolicy" 实例化。
  3. 在 tests/dlt/scheduler/ 增加单测。

新增 KV 分配器

  1. 实现 device_aware_block_allocator.h 接口。
  2. 在 self_attn_block_manager.cpp 添加构造分支。
  3. 暴露指标到 HitRateCalculator。

新增 Python 插件

  1. 在 mindie_llm/text_generator/plugins/ 新建子模块。
  2. 继承 plugin.py 中的 Plugin 接口（before_forward / after_forward / before_sample 等钩子）。
  3. 在 plugin_manager.py 注册类型。
  4. 通过 config.json → ModelConfig.pluginParams.<name>.enable=true 启用。

新增 endpoint 协议

  1. 在 src/server/endpoint/ 新增 my_proto_wrapper。
  2. 实现请求解码 / 响应编码。
  3. 在 endpoint.cpp 注册 URL 路由。
  4. 更新 API 矩阵 与文档。

分支与提交规范

  • 主分支：master — 稳定版本，发布出口。
  • 开发分支：dev — 日常合入；新特性建议从 dev 拉分支。
  • 版本分支：v3.0.0.beta.x 等，发布前的稳定化分支。
  • 特性分支命名：feat/<description> / fix/<issue-id> / doc/<topic>。

commit message 推荐 Conventional Commits 风格：

feat(scheduler): add layerwise FCFS policy
fix(block_manager): correct ref count on swap
doc(wiki): add architecture overview
perf(quant): fuse W8A8 dequant with matmul

PR 流程

  1. Fork 上游仓库（GitCode）。
  2. 本地 clone，从 dev 拉特性分支。
  3. 实现并补单测；本地跑 pre-commit run --all-files + 相关单测全过。
  4. 提交、推送至 fork。
  5. 在 GitCode 上发 PR，标题用 Conventional Commits 格式； 正文描述：动机 / 设计 / 兼容性 / 测试。
  6. 等待 CI 通过 + 至少 1 名 Committer 检视。
  7. 评审意见落实 → 重新提交（rebase 优于 merge）。
  8. 获得足够 Approvals → CI 自动合入。

安全

  • 不要在代码 / 日志 / commit message 中带任何 token、密钥、内部 URL。
  • 发现安全漏洞请不要在 issue 公开，按 security.md 的流程 通过邮件联系核心维护者。
  • 修改加密 / 鉴权 / 网络相关代码时，必须经过资深维护者评审。

文档

  • 用户面向变更 → 同步更新 docs/zh/user_guide/。
  • 架构 / 设计变更 → 同步更新 docs/zh/developer_guide/。
  • 本 Wiki 是非官方知识库，可作为内部参考；如有同步必要，请额外更新本目录。

PR 自检清单

  • ✅ 改动在 dev 分支衍生；commit message 规范
  • ✅ pre-commit run --all-files 通过
  • ✅ 新增 / 修改的代码有相应单测
  • ✅ 涉及 config.json 字段的变更有 param_checker 校验
  • ✅ 文档同步（docs/zh/... 与本 Wiki）
  • ✅ 兼容性影响在 PR 描述中标明
  • ✅ 没有遗留 TODO / 注释掉的代码 / 调试 print
