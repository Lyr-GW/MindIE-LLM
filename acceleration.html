加速特性

本章介绍那些在并行 / 量化之外的「软加速」手段：调度优化、复用与跳算、 投机解码、KV 池化、思考与函数调用等，每项都给出原理 + 启用方法 + 典型收益。

基线：Continuous Batching + PagedAttention

这两项是 MindIE-LLM 的默认能力，无需开关：

  • Continuous Batching：每轮 forward 重新组 batch，结束的请求立即被新请求填补。
  • PagedAttention：KV Cache 分块管理（详见 Block Manager），消除显存碎片。

Prefix Cache（前缀缓存）

多个请求若有相同前缀（system prompt / 模板 / 历史对话），其前缀 KV 只需 一次 prefill。

  • 命中：通过 PrefixCacheBlockAllocator 匹配 block hash。
  • 收益：命中部分省去整段 prefill — TTFT 显著下降。
  • 统计：HitRateCalculator 将命中率暴露在 /metrics。
  • 启用：pluginParams.prefix_cache.enable=true。

KV Cache 池化

把 NPU 显存之外的 CPU DRAM（甚至 SSD via mmap）也纳入 KV 缓存池。

  • 实现：CpuNpuBlockAllocator 管理两级存储，热数据留 NPU、冷数据下放 CPU。
  • 价值：在显存有限的卡上把 prefix cache 命中率推到极致 — 历史对话 的前缀 KV 不再被 LRU 驱逐。
  • 启用：pluginParams.kv_pool.enable=true，并配置 cpuMemSize。

SplitFuse（Chunk Prefill）

把超长 prompt 的 prefill 分成多个 chunk，与其他请求的 decode 同 step 执行。

  • 问题：朴素调度下，长 prefill 会让所有 decode 请求停顿 N step。
  • 方案：每 step 执行 1 chunk prefill + 当前所有 decode； N step 后 prefill 完成，过渡到 decode 阶段。
  • 价值：长尾请求不再阻塞短尾请求；TTFT、TPOT 同时改善。
  • 启用：pluginParams.split_fuse.enable=true， chunkTokens 控制 chunk 大小。

异步调度

把调度循环（host 上的请求组装 / 结果回收）与 NPU 计算解耦：当 NPU 在做第 N+1 step 时，host 可以同时为 N+2 step 做数据准备。

  • 核心条件：maxBatchSize 大、IO 长。
  • 实现：调度线程与执行线程分离，通过双 buffer 协作。
  • 启用：pluginParams.async_schedule.enable=true， 与 maxQueueDelayMicroseconds 配合。

SLO 调度优化

结合 latency_predictor，在保证既定 TTFT/TPOT SLO 的前提下最大化吞吐。决策核心：

  1. 预估「如果加入这个请求，本轮 batch 是否会让某些在飞请求超 SLO」。
  2. 预估「如果不加，等待该请求超等待 SLO」。
  3. 取「全局 SLO 违反成本最低」的方案。

实战中可以同时设置 hard SLO（必达）与 soft SLO（柔性），引擎会按权重做资源分配。

Micro Batch

把大 batch 切成多个小 micro batch 轮转执行，使数据加载、 集合通信、计算可以重叠。

  • 价值：降低集合通信对吞吐的占比，特别在 TP 较大时。
  • 限制：与 CP / SP / Prefix Cache / KV Pool 等部分特性互斥 （详见 兼容矩阵）。

投机解码（Speculative Decoding）/ 并行解码

用一个 小 draft 模型快速生成 N 个候选 token，再用主模型一次性校验。

  • 价值：把多个 decode step 压缩成一次 forward，提高算力利用率。
  • 插件：la（Lookahead Decoding） 以及 MTP。
  • 关键参数：draft_steps（候选数）、verify_strategy。

Lookahead Decoding（LA）

不需要额外 draft 模型 — 用主模型自身的 N-gram 缓存做预测，验证阶段并行执行。

  • 对开放问答 / 编程 / 多轮对话效果好（重复 pattern 多）。
  • 对短回答场景收益较小。

MTP（Multi-Token Prediction）

模型本身被设计 / 训练为一次预测多个 token。MindIE-LLM 在 plugins/mtp 实现对应的 sampling 与校验逻辑。

  • 需要权重支持：例如 DeepSeek-V3 系列附带 MTP head。
  • 价值：每 step 输出多个 token，吞吐显著提升。
  • 限制：长上下文（128k）建议关闭，避免精度抖动。

Memory Decoding

把历史 KV / token 序列作为「记忆」，在 decode 时用快速近似检索预测下一个 token， 再用主模型校验。

  • 本质是投机解码的另一种 draft 来源 — 「检索」而非「小模型」。
  • 对长文档问答类业务有奇效。
  • 插件位于 plugins/memory_decoding。

Layer Skipped（跳层推理）

对易决策 token（高 confidence）跳过部分层。

  • 实现于 plugins/layer_skipped，与 modeling 中的层级 forward 钩子配合。
  • 典型节省 10–30% 的 decode 时间。
  • 需评估精度损失。

结构化输出（Structured Output）

在采样阶段引入约束（JSON Schema、正则、上下文无关文法），保证输出格式合规。

  • 插件：plugins/structured_output。
  • 关键算法：FSM / Pushdown automaton 限制每步可选 token 集合。
  • 对 Function Call、API 编排等场景刚需。

Function Call

支持 OpenAI 风格的工具 / 函数调用协议：

  • 请求里附带 tools 列表与 schema。
  • 模型按训练好的对话模板生成 tool_calls。
  • 引擎侧识别并把 tool_calls 结构化，返回标准 JSON。
  • 客户端执行工具 → 把结果作为下一轮 input 喂回模型。

思考解析与思考预算

面向推理增强模型（DeepSeek-R1 / Qwen-QwQ 等）的两项交互特性：

  • 思考解析：把 <think> ... </think> 这类 reasoning 段从最终回答中拆出。流式场景同时支持「思考流」与「回答流」分离推送。
  • 思考预算（thinking_budget）：限制 reasoning token 数量， 避免模型陷入过长自我对话；预算耗尽自动切换到「直答」模式。

权重离线切分

大模型加载耗时主要在「读盘 + 切分到各 NPU」。本特性把切分结果提前 落盘到 tmpfs，启动时只做拷贝：

  • 显著缩短服务冷启动时间（典型从分钟级到秒级）。
  • 需要 host 内存承担 tmpfs 体量。
